## 3. FINDINGS

### F-048: Stopping All Lanes via Web UI Leaves `Paradiso` Daemon Running, Permanently Locking Settings & Simulation Clock Reset (`HTTP 409`)

- **Severity:** HIGH
- **Confidence:** CONFIRMED
- **Category:** STATE-MACHINE / API / UI
- **Invariant:** I-7 (Honest API), I-8 (State Convergence), I-10 (Hot-Reload Safety), BG-001 (Idle-Only Guardrail)
- **Location:** `paradiso/services/paradiso.py:start_lane:90-110`, `paradiso/services/paradiso.py:stop_lane:112-126`, `paradiso/controllers/paradiso_controller.py:status:48-53`, `paradiso/controllers/settings_controller.py:update_settings:35-48`, `paradiso/controllers/settings_controller.py:reset_simulation_clock:77-90`, `paradiso/web/static/js/app.js:checkSchedulerStatus:554-566`, `paradiso/web/static/js/app.js:updateSettingsLockUI:1931-1949`

**OBSERVATION**
The Web UI (`index.html`) starts and stops lanes exclusively through per-lane endpoints (`startLane(lane)` $\rightarrow$ `POST /api/paradiso/lane/start` and `stopLane(lane)` $\rightarrow$ `POST /api/paradiso/lane/stop`). There is no button in `index.html` wired to `stopScheduler()` (`POST /api/paradiso/stop`).
When `Paradiso.start_lane()` is called (`paradiso/services/paradiso.py:103-106`), it starts the background daemon thread `self._thread`:
```python
if not self.is_running():
    self._stop_event = threading.Event()
    self._thread = threading.Thread(target=self._loop, daemon=True)
    self._thread.start()
```
However, when `Paradiso.stop_lane()` is called (`paradiso/services/paradiso.py:112-126`):
```python
self.intraday_service.stop_lane(norm)
self._lane_transition_times[norm] = time.time()
self._last_transition_time = time.time()
return TransitionResult(True, "stopped", 0.0)
```
Even when all three lanes (`type_a`, `type_b`, `type_c`) have been stopped (`self.intraday_service.is_active == False`), `Paradiso.stop_lane()` never sets `self._stop_event` or stops `self._thread`. Consequently, `self.paradiso.is_running()` remains `True` indefinitely.

**EVIDENCE**
1. Trace across Frontend and Backend after starting Lane A and then stopping Lane A:
   - `GET /api/paradiso/lanes/status` returns `running: false` for all 3 lanes (`type_a`, `type_b`, `type_c`). The UI Top Bar and Dashboard display `○ Standby` and `○ Scheduler: Standby` (`app.js:528`).
   - `GET /api/paradiso/status` (`paradiso_controller.py:51`) returns `{"ok": true, "running": true}` because `self.paradiso.is_running()` inspects `self._thread.is_alive() and not self._stop_event.is_set()`.
   - `checkSchedulerStatus()` (`app.js:559`) sets `isSchedulerRunning = true` and calls `updateSettingsLockUI()` (`app.js:1936`), which displays `#settings-locked-banner` (*"Configuration Locked: Settings cannot be modified while Paradiso scheduler is running... Stop the scheduler before modifying settings"*) and disables `#btn-save-settings`.
   - `applySimulationSettings()` (`app.js:2062`) blocks changes because `isSchedulerRunning === true`.
   - `SettingsController.update_settings()` (`settings_controller.py:38`) and `SettingsController.reset_simulation_clock()` (`settings_controller.py:80`) evaluate `if self.paradiso and self.paradiso.is_running(): is_active = True` and return **HTTP 409 Conflict**.
2. Reproduced deterministically via `py -3 paradiso/artifacts/audits/poc/poc_f048_f052_frontend_backend_integrity.py` (`test_f048_stopping_all_lanes_leaves_scheduler_locked_and_blocks_settings_409`):
   ```
   AssertionError: True is not false : F-048 Defect: /api/paradiso/status still reports running=True after all lanes are stopped!
   ```

**CONSEQUENCE**
Once an operator starts any lane via the Web UI, stopping all lanes via the Web UI does not release the BG-001 configuration lock. The UI simultaneously tells the operator that the scheduler is in `○ Standby` (with all Stop buttons hidden and only `▶ Start` buttons shown) while locking Settings and Simulation Clock Reset with instructions to *"Stop the scheduler first"*. The operator is permanently locked out of modifying Settings or resetting the Simulation Clock for the remainder of the server process lifetime.

**ROOT-CAUSE HYPOTHESIS** (non-authoritative)
Unverified hypothesis: `Paradiso.is_running()` and `Paradiso.stop_lane()` were written when a global start/stop button controlled `self._thread`; when the UI transitioned to independent 3-lane controls, `stop_lane()` did not stop the daemon loop (or `is_running()` / `SettingsController` continued checking thread liveness regardless of whether `intraday_service.is_active` or `has_active_runs` is true).

**VERIFICATION CRITERION**
After starting one or more lanes via `POST /api/paradiso/lane/start` and subsequently stopping all active lanes via `POST /api/paradiso/lane/stop` (with no jobs in flight), `GET /api/paradiso/status` must report `"running": false`, the frontend `#btn-save-settings` and Testing Lab simulation controls must be unlocked, and `POST /api/settings` and `POST /api/settings/simulation/reset` must succeed with HTTP 200 OK.

### F-049: `POST /api/automation/enable` Is Completely Orphaned from the Web UI, Trapping Disabled and Failed Reports Without Recovery Controls

- **Severity:** HIGH
- **Confidence:** CONFIRMED
- **Category:** UI / API
- **Invariant:** I-7 (Honest API / UI), I-8 (Queue / Storage / Memory Convergence)
- **Location:** `paradiso/web/static/js/app.js:filterAutomationsCatalog:864-922`, `paradiso/web/static/js/app.js:renderLaneATable:650-681`, `paradiso/web/static/js/app.js:renderLaneBTable:683-721`, `paradiso/web/static/js/app.js:renderLaneCTable:723-763`, `paradiso/web/static/js/app.js:disableReport:1277-1308`

**OBSERVATION**
In `paradiso/web/static/js/app.js`:
1. `disableReport(name)` (lines 1278–1286) prompts the operator with:
   ```javascript
   warning: '⚠️ While disabled, this report will not be dispatched autonomously or manually until re-enabled.'
   ```
2. `ExecutionController.run_automation()` (`paradiso/controllers/execution_controller.py:49-54`) rejects manual runs of `"Disabled"` or `"Failed"` reports with HTTP 409:
   ```python
   "error": f"Cannot execute report '{name}': report is {status_label}. Re-enable it before running."
   ```
3. However, `app.js` and `index.html` contain **zero references to `/api/automation/enable`** and define no `enableReport()` handler or UI button.
4. In `filterAutomationsCatalog()` (`app.js:910-917`):
   ```javascript
   ${item.status !== 'Disabled' ? `
   <button type="button" class="btn-card-action" onclick="disableReport('${escapeHtml(item.name)}')" title="Disable report from scheduling">
       ⏸ Disable
   </button>` : ''}
   <button type="button" class="btn-card-action" onclick="deleteReport('${escapeHtml(item.name)}')" title="Delete report from catalog">
       🗑 Delete
   </button>
   ```
   When a report is `Disabled`, the `⏸ Disable` button disappears and no `▶ Enable` button is rendered in its place. When a report is `Failed`, the card still displays `⏸ Disable` rather than a re-enable action, and the Lane A, Lane B, and Lane C tables provide no re-enable action either.
5. Additionally, `filterAutomationsCatalog()` (`app.js:865-870`) checks `Completed`, `Running`, `Retrial`, and `Failed`, but omits `else if (item.status === 'Disabled') badgeClass = 'badge-disabled';`, causing `Disabled` reports in the Automations Catalog to render with the blue `badge-waiting` class.

**EVIDENCE**
Reproduced deterministically via `py -3 paradiso/artifacts/audits/poc/poc_f048_f052_frontend_backend_integrity.py` (`test_f049_enable_endpoint_connected_in_frontend_and_disabled_badge_styled`):
```
AssertionError: '/api/automation/enable' not found in ... : F-049 Defect: /api/automation/enable is never called anywhere in app.js! Disabled/Failed reports cannot be re-enabled from the UI.
```

**CONSEQUENCE**
Although `POST /api/automation/enable` was implemented on the backend (F-036, F-043, F-045) specifically to prevent operators from having to perform destructive full-queue resets (`POST /api/automations/reset`), the feature is unreachable from the Web UI. Any report that is disabled via the UI's `⏸ Disable` button or that enters terminal `Failed` status is trapped in the UI with no non-destructive recovery path.

**VERIFICATION CRITERION**
The Web UI (`app.js`) must expose an interactive re-enable control wired to `POST /api/automation/enable` for reports in `Disabled` or `Failed` status (in the Automations Catalog and/or Lane views), and `filterAutomationsCatalog()` must assign `badge-disabled` styling when `item.status === 'Disabled'`.

### F-050: Hardcoded Frontend Retry Telemetry Falsely Reports `1 / 3` Error Retries on Zero-Penalty Dependency Skips and Masks Actual Retry Counts

- **Severity:** MEDIUM
- **Confidence:** CONFIRMED
- **Category:** UI / API
- **Invariant:** I-2 (Dependency Wait vs. Error Retry), I-7 (Honest API / UI), I-8 (State Convergence)
- **Location:** `paradiso/web/static/js/app.js:renderLaneATable:668`, `paradiso/web/static/js/app.js:renderLaneBTable:701`, `paradiso/web/static/js/app.js:renderLaneCTable:741`, `paradiso/controllers/automation_controller.py:get_automations:31-33`

**OBSERVATION**
In `AutomationController.get_automations()` (`paradiso/controllers/automation_controller.py:31-33`), the endpoint returns `self.automation_service.get_all(serialized=True)` without enriching report objects with live retry counts (`self.intraday_service.retry_counts`) or `max_retries`.
In `paradiso/web/static/js/app.js`, all three lane table renderers (`renderLaneATable` line 668, `renderLaneBTable` line 701, `renderLaneCTable` line 741) compute the **Error Retries** column via a hardcoded status ternary:
```javascript
const retries = item.status === 'Failed' ? '3 / 3' : (item.status === 'Retrial' ? '1 / 3' : '0 / 3');
```

**EVIDENCE**
1. Under Invariant I-2, when a report outputs `SKIPPED: Missing dependency 'X'`, `IntradayService` sets `status = "Retrial"` and keeps `self.retry_counts[name] == 0` (zero retry penalty). However, `renderLaneATable`, `renderLaneBTable`, and `renderLaneCTable` unconditionally render `1 / 3` under **Error Retries** whenever `item.status === 'Retrial'`.
2. When a report suffers 2 genuine runtime errors (`status = "Retrial"`, `self.retry_counts[name] == 2`), the UI still renders `1 / 3`.
3. When an unstarted report is marked `Failed` at the 22:00 cutoff (`self.retry_counts[name] == 0`), the UI renders `3 / 3`.
4. Reproduced deterministically via `py -3 paradiso/artifacts/audits/poc/poc_f048_f052_frontend_backend_integrity.py` (`test_f050_automations_api_and_ui_accurate_retry_counts`).

**CONSEQUENCE**
Operators monitoring Lane A, Lane B, or Lane C tables are shown fabricated error retry counts that contradict backend state and violate Invariant I-2 by displaying a `1 / 3` error penalty on zero-penalty dependency rotations.

**VERIFICATION CRITERION**
`GET /api/automations` (or the frontend telemetry) must expose actual retry counts from `IntradayService.retry_counts` (and `max_retries`), and `renderLaneATable`, `renderLaneBTable`, and `renderLaneCTable` must render the true retry count (e.g., `0 / 3` for a dependency skip in `Retrial`, `2 / 3` after two genuine errors).

### F-051: Silent Frontend Suppression of HTTP 409 Error on Simulation Clock Reset and Hidden Toast Notification on Report Registration

- **Severity:** MEDIUM
- **Confidence:** CONFIRMED
- **Category:** UI / HONEST API
- **Invariant:** I-7 (Honest API / UI), BG-001
- **Location:** `paradiso/web/static/js/app.js:triggerClockReset:2032-2047`, `paradiso/web/static/js/app.js:handleAddReportSubmit:1174-1188`

**OBSERVATION**
Two frontend action handlers fail to surface backend responses to the operator:
1. In `triggerClockReset()` (`paradiso/web/static/js/app.js:2032-2047`):
   ```javascript
   async function triggerClockReset() {
       try {
           const res = await fetch('/api/settings/simulation/reset', { method: 'POST' });
           const data = await res.json();
           if (data.ok) {
               showSettingsToast('Simulation clock reset to midnight.', 'success');
               showTestingToast('Simulation clock reset to midnight.', 'success');
               fetchDashboardStats();
               fetchTimeline();
           }
       } catch (e) { ... }
   }
   ```
   When `POST /api/settings/simulation/reset` returns HTTP `409 Conflict` (`data.ok === false`, per F-042 when a lane or job is active), `fetch()` resolves normally without throwing, `if (data.ok)` is false, and there is no `else` branch.
2. In `handleAddReportSubmit()` (`paradiso/web/static/js/app.js:1174-1178`):
   ```javascript
   if (data.ok) {
       closeAddReportModal();
       const laneLabel = report_type === 'type_b' ? 'Lane B' : (report_type === 'type_c' ? 'Lane C' : 'Lane A');
       showSettingsToast(data.message || `Report '${name}' registered successfully in ${laneLabel}!`, 'success');
   ```
   `showSettingsToast()` writes into `#settings-alert-banner`, which resides inside `<div id="view-settings" style="display: none;">` (`index.html:772, 779`). The `+ Add Report` buttons exist on `#view-dashboard`, `#view-automations`, `#view-type-a`, `#view-type-b`, and `#view-type-c`—never on `#view-settings`.

**EVIDENCE**
Reproduced deterministically via `py -3 paradiso/artifacts/audits/poc/poc_f048_f052_frontend_backend_integrity.py` (`test_f051_clock_reset_surfaces_409_and_add_report_shows_visible_toast`).

**CONSEQUENCE**
1. Clicking `↺ Reset to Midnight` in the Testing Lab while any lane or job is running fails silently in the browser with zero error banner or toast explaining the BG-001 / HTTP 409 rejection.
2. Registering a new report via the Add Report modal never displays a visible confirmation toast because the toast is rendered inside a hidden tab container.

**VERIFICATION CRITERION**
1. `triggerClockReset()` must handle `!data.ok` (including HTTP 409 responses) by displaying the backend error message via `showTestingToast(..., 'error')` and/or `showToast(..., 'error')`.
2. `handleAddReportSubmit()` must invoke `showToast(...)` so the confirmation toast is visible regardless of which tab the operator is viewing.

### F-052: Unbound Lane B "Active Workers" Metric Card (`0 In-Flight`) and Residual `EOD (21:00)` Schedule Labels in `index.html`

- **Severity:** LOW
- **Confidence:** CONFIRMED
- **Category:** UI / DOC-DRIFT
- **Invariant:** I-3 (Window & Schedule Rules), I-7 (Honest UI)
- **Location:** `paradiso/web/templates/index.html:168, 465-469, 535, 570`, `paradiso/web/static/js/app.js:updateLaneUI:468-498`

**OBSERVATION**
1. In `#view-type-b` (`paradiso/web/templates/index.html:465-469`), the second metric card is static HTML without an `id`:
   ```html
   <div class="metric-card">
       <div class="metric-label">Active Workers</div>
       <div class="metric-num" style="font-size: 16px; font-weight: 700; color: #34d399; margin-top: 8px;">0 In-Flight</div>
       <div style="font-size: 11px; color: var(--text-muted); margin-top: 6px;">Multiple jobs run simultaneously</div>
   </div>
   ```
   Although `fetchLanesStatus()` (`app.js:510`) polls `GET /api/paradiso/lanes/status` every second and stores `lanesState.type_b.active_runs = laneInfo.running_count || 0`, `updateLaneUI()` (`app.js:468-498`) only updates the DOM metric card for `laneKey === 'type_a'` and never updates Lane B's `Active Workers` count.
2. In `paradiso/web/templates/index.html`, three UI labels still state `EOD (21:00)` instead of `EOD (20:30)`:
   - Line 168 (Dashboard Lane C card): `Fixed time-pinned reports for BOD (07:00), Mid-day (12:00), EOD (21:00), and custom slots.`
   - Line 535 (Type C hero subtitle): `...BOD (07:00), Mid-day (12:00), EOD (21:00), or custom HH:MM.`
   - Line 570 (Type C metric card): `<div class="metric-label">EOD Slot (21:00)</div>`

**EVIDENCE**
Reproduced deterministically via `py -3 paradiso/artifacts/audits/poc/poc_f048_f052_frontend_backend_integrity.py` (`test_f052_lane_b_active_workers_bound_and_eod_2030_consistent`).

**CONSEQUENCE**
1. While Type B recurring reports are actively executing in flight, the Lane B view's `Active Workers` metric card remains stuck at `0 In-Flight`.
2. Operators viewing the Dashboard and Lane C view see `EOD (21:00)` on the page header and metric card, contradicting the `20:30` EOD milestone enforced by the Add Report Modal, backend scheduler (`F-047`), and `21:00` `WAITING_TO_CLOSE` cutoff rules (`F-027`).

**VERIFICATION CRITERION**
1. The Lane B `Active Workers` metric element in `index.html` must have a dedicated DOM ID (including `metric-b-active`) updated by `updateLaneUI('type_b')` in `app.js` using `lanesState.type_b.active_runs`.
2. All `EOD (21:00)` references in `index.html` (lines 168, 535, 570) must be aligned to `EOD (20:30)`.

## 4. REFUTED HYPOTHESES

1. **Hypothesis:** `DELETE /api/automation/delete/<name>` or `POST /api/automation/disable` can be triggered via UI without confirmation, or fails to URL-encode special characters in report names.

2. **Hypothesis:** Stored XSS via report `name`, `team`, `owner`, `last_output`, or timeline `title`/`description` when rendering dynamic tables in `app.js`.
   - **Result:** **REFUTED.** `escapeHtml()` (`app.js:582-590`) is consistently applied to user-controlled fields across `fetchAutomations()`, `renderLaneATable()`, `renderLaneBTable()`, `renderLaneCTable()`, `filterAutomationsCatalog()`, `fetchTimeline()`, `filterTimelineEvents()`, and `renderExecutionsTable()`, and `openLogModal()` uses `innerText`.
