## 3. Deep-Dive Vulnerability Dossier

### F-040: `POST /api/automation/run` Bypasses "Disabled" State and Re-Arms Quarantined Automations

- **Severity:** HIGH
- **Invariants Breached:** I-7, I-8
- **Source Location:** `paradiso/controllers/execution_controller.py:run_automation:38-51`, `paradiso/services/intraday_service.py:trigger_manual_run:1195-1216`
- **Adversarial Asset:** `paradiso/artifacts/audits/poc/poc_f040_disabled_report_manual_run_bypass.py`

#### OBSERVATION
In `ExecutionController.run_automation()`, lines 38–51 permit manual execution for Type B and Type C reports:
```python
if report.report_type in ["type_b", "type_c"]:
    if self.intraday_service:
        status = self.intraday_service.resolve_status()
        if status != "OPEN" and not getattr(self.intraday_service, "force_open", False):
            ...
        success = self.intraday_service.trigger_manual_run(name)
```
In `IntradayService.trigger_manual_run()`, lines 1195–1216 verify open window status and launch `_trigger_type_b_report` or `_trigger_type_c_report`:
```python
def trigger_manual_run(self, name: str) -> bool:
    report = self.automation_service.get_by_name(name)
    if not report or report.report_type == "type_a":
        return False
    ...
```
Neither `run_automation()` nor `trigger_manual_run()` evaluates whether `report.status == "Disabled"`.

#### EVIDENCE
Demonstrated deterministically in `poc_f040_disabled_report_manual_run_bypass.py`:
1. Register a Type B or Type C report and call `POST /api/automation/disable`. Its status in `storage/automations.json` is `"Disabled"`.
2. Submit `POST /api/automation/run` with `{"name": "Quarantined_Feed"}` during `OPEN`.
3. The API responds with HTTP 200 Created (`"Manual run triggered for TYPE_B report 'Quarantined_Feed'."`).
4. The subprocess is dispatched on the host OS.
5. In `ExecutionService.execute_report()`, line 36 updates the automation status to `"Running"`. When execution completes, line 83 updates the status to `"Completed"` (or `"Failed"`).
6. The persistent `"Disabled"` state is permanently erased from `automations.json` without an operator ever calling `POST /api/automation/enable`. On subsequent scheduler ticks, the engine sees the report is no longer `"Disabled"` and resumes automated scheduling.

#### CONSEQUENCE
Quarantined or broken automations can be accidentally executed via API or UI, launching unauthorized code and permanently stripping the safety disabling flag.

#### VERIFICATION CRITERION
`ExecutionController.run_automation()` and `IntradayService.trigger_manual_run()` must reject manual execution requests for any report whose status is `"Disabled"` (e.g. returning HTTP 409 Conflict) without launching a subprocess or modifying storage.

### F-041: Lane B Dispatches Permanently Failed Reports in Unbounded Infinite Loop

- **Severity:** CRITICAL
- **Invariants Breached:** I-1, I-6
- **Source Location:** `paradiso/services/intraday_service.py:tick:620-639`, `paradiso/services/intraday_service.py:_trigger_type_b_report:998-1042`
- **Adversarial Asset:** `paradiso/artifacts/audits/poc/poc_f041_lane_b_infinite_exhausted_dispatch.py`

#### OBSERVATION
In `IntradayService.tick()`, lines 620–639 evaluate Lane B recurring reports:
```python
b_reports = self.automation_service.get_by_type("type_b")
for rep in b_reports:
    if rep.status == "Disabled":
        continue
    if rep.name in self.active_runs_type_b:
        continue  # Self-overlap prevention
    last_run = self.type_b_last_run.get(rep.name)
    interval_sec = (rep.interval_minutes or 30) * 60
    should_run = False
    if last_run is None:
        should_run = True
    else:
        elapsed = (CLOCK.now() - last_run).total_seconds()
        if elapsed >= interval_sec:
            should_run = True
    if should_run:
        self._trigger_type_b_report(rep.name, today_date)
```
Lane B only skips reports with `rep.status == "Disabled"`. It does not check if `rep.status == "Failed"` or whether the report has exhausted its retry budget.

#### EVIDENCE
Demonstrated deterministically in `poc_f041_lane_b_infinite_exhausted_dispatch.py`:
1. Register a Type B report with `interval_minutes: 15` and `max_retries: 3`.
2. Induce 3 consecutive execution errors. `_handle_failure()` executes the terminal branch: sets `rep.status = "Failed"`, logs `"{name} permanently failed (Exceeded max retries (3/3))"`, and records `result="failed"` in `day.reports_ran`. Line 1018 records `self.type_b_last_run[name] = CLOCK.now()`.
3. Advance clock by 20 minutes (exceeding `interval_sec = 900`).
4. `tick()` evaluates `elapsed >= interval_sec` as `True`. Because `rep.status` is `"Failed"` (not `"Disabled"`), line 638 dispatches `_trigger_type_b_report()` again.
5. In `_handle_failure()`, `attempts` increments to 4, 5, 6, etc. The failing subprocess is re-launched every 15 minutes perpetually throughout the day.

#### CONSEQUENCE
Lane B reports that encounter fatal runtime errors never cease execution; they enter an unbounded loop consuming CPU, spawning failing host processes, and flooding intraday timeline history and storage with failure events.

#### VERIFICATION CRITERION
`IntradayService.tick()` must suppress automatic Lane B dispatch for reports that have reached terminal `"Failed"` status or exhausted their retry budget for the calendar day. Resuming execution must require administrative re-enablement or operational reset.

### F-042: `POST /api/settings/simulation/reset` Bypasses BG-001 Idle-Only Guardrail

- **Severity:** MEDIUM
- **Invariants Breached:** BG-001, I-3, I-7
- **Source Location:** `paradiso/controllers/settings_controller.py:reset_simulation_clock:77-84`
- **Adversarial Asset:** `paradiso/artifacts/audits/poc/poc_f042_simulation_reset_bypasses_idle_guardrail.py`

#### OBSERVATION
While `SettingsController.update_settings()` enforces the BG-001 guardrail (lines 36–48) rejecting configuration mutations while the scheduler is active or jobs are in flight, `reset_simulation_clock()` (lines 77–84) completely omits activity checks:
```python
def reset_simulation_clock(self):
    CLOCK.reset_simulation()
    return jsonify({
        "ok": True,
        "message": "Simulation clock reset to midnight.",
        "time": CLOCK.time_str(),
        "date": CLOCK.formatted_date()
    }), 200
```

#### EVIDENCE
Demonstrated deterministically in `poc_f042_simulation_reset_bypasses_idle_guardrail.py`:
1. Start the scheduler with an active lane or launch an in-flight execution.
2. Submit `POST /api/settings/simulation/reset`.
3. The endpoint returns HTTP 200 OK.
4. The virtual clock abruptly rewinds from mid-day (e.g. 14:00) to 00:00 midnight.
5. In `IntradayService.tick()`, `resolve_status()` changes from `OPEN` to `WAITING_TO_OPEN`. Active dispatching halts mid-cycle.
6. Currently executing subprocesses finish after the rewind. Their execution completion timestamp is stamped with `CLOCK.formatted_now()` (`00:00:xx AM`), resulting in an inverted record where `finished_at < started_at`.

#### CONSEQUENCE
Violates the BG-001 idle-only invariant; allows uncoordinated clock tampering during active runs, resulting in timeline chronological inversion and unexpected queue freezes.

#### VERIFICATION CRITERION
`POST /api/settings/simulation/reset` must enforce the BG-001 idle-only check, rejecting requests with HTTP 409 Conflict if the scheduler is active or jobs are in flight.
