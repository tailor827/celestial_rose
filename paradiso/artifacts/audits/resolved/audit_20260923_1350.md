- **Status:** **RESOLVED**
- **Evaluation:**
  - Implemented state tracking in `StorageBase._global_corrupted_states` keyed by canonical path mapping to `(st_mtime_ns, st_size)`.
  - In-memory cache hit immediately skips duplicate backup creation.
  - Cold reboot resilience: If the in-memory cache is empty (e.g. after daemon restart), it globs for existing `*_corrupted_*.bak` files, loads the latest backup, and compares raw byte contents against the damaged file (`latest_bak.read_bytes() == self.file_path.read_bytes()`). If identical, backup creation is skipped and the cache key is re-populated.

## 4. ADVERSARIAL CRITIQUE & OBSERVATIONS ("DOING OUR WORST")

### A. Subtle Edge-Cases on F-007 Implementation (`models/storage_base.py`)
1. **Sorting Granularity on High-Frequency Thrashing:**
   - **Observation:** `existing_baks = sorted(..., key=lambda p: p.stat().st_mtime)` sorts backups using floating-point `st_mtime`. On certain legacy filesystems (e.g., FAT32 or network shares), mtime resolution is limited to 1-2 seconds.
   - **Consequence:** If multiple distinct corruptions occur within the same integer second, sorting by `st_mtime` could result in indeterminate ordering for the rotation prune.
   - **Mitigation/Recommendation:** While NTFS provides 100ns precision, sorting by `(p.stat().st_mtime_ns, p.name)` provides deterministic ordering across all filesystem types.
2. **Byte Comparison Overhead on Pathological JSON Bloat:**
   - **Observation:** `latest_bak.read_bytes() == self.file_path.read_bytes()` reads the entirety of the corrupted file and the backup into memory during cold boot.
   - **Assessment:** Safe for Paradiso because storage files (`automations.json`, `intraday.json`) are typically $< 500\text{ KB}$, and the `st_size` equality check short-circuits reading unequal files.

### B. Proactive Threat-Modeling for Upcoming Phase 6 (BG-002 & F-009)

As Builder prepares to implement Phase 6, the following architectural vulnerabilities must be defended:

#### 1. The `start_fresh_run()` In-Flight Amnesia Trap (`services/intraday_service.py:119-136`)
- **Vulnerability:** When `/api/paradiso/start` is called, `Paradiso.start()` executes:
  ```python
  self.intraday_service.start_fresh_run()
  if self.is_running():
      return True
  ```
- **Consequence:** If `/api/paradiso/start` is invoked while the scheduler is **already running**:
  1. `self.retry_counts.clear()` wipes all retry and penalty counters for currently executing jobs.
  2. The loop over `self.automation_service.get_all()` marks any report with status `"Running"` back to `"Waiting"` with message `"Reset from previous session shutdown/crash"`, **even though the subprocess is actively running on the OS!**
  3. When the active subprocess completes, its watcher attempts to write success/failure to a report that the state machine now considers `"Waiting"`.
- **Auditor Requirement for BG-002:** Calling `start()` on an already running or starting scheduler must be rejected immediately at the controller/service boundary before `start_fresh_run()` is triggered.

#### 2. The Zombie Thread Race on Rapid Start/Stop Cycling
- **Vulnerability:** If `stop()` is called, it sets `self._stop_event.set()` and sets `self._thread = None`. If `start()` is called immediately within the scheduler's tick interval (0.5s–15s):
  ```python
  self._stop_event.clear()
  self._thread = threading.Thread(target=self._loop, daemon=True)
  self._thread.start()
  ```
  The terminating loop thread may not have woken up from `self._stop_event.wait(timeout=self.interval)`. When `_stop_event.clear()` is called by `start()`, the old thread wakes up, finds `_stop_event` is NO LONGER SET, and **resumes ticking**, resulting in dual parallel scheduler loops running simultaneously!
- **Auditor Requirement for BG-002:** `stop()` must synchronously join the old thread with a short timeout (`self._thread.join(timeout=2.0)`) or instantiate a fresh `threading.Event()` for each thread lifecycle rather than clearing a shared event.
