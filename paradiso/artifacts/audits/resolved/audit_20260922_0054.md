## 3. FINDINGS

### F-001: Deleting an executing report via API causes permanent scheduler queue deadlock

- **Severity:** CRITICAL
- **Confidence:** CONFIRMED
- **Category:** QUEUE
- **Invariant:** I-1, I-8
- **Location:** `controllers/automation_controller.py:delete_automation:65-76`, `services/execution_service.py:execute_report:20-22`, `services/intraday_service.py:tick:243-246`

**OBSERVATION**  
When an automation currently executing in `self.current_runs` is deleted via `DELETE /api/automation/delete/<name>`, the controller removes the record from `automations.json` and evicts the name from `waitlist`, but does not remove it from `current_runs` or terminate the running subprocess. When the subprocess exits with a dependency skip (or an error within retry limits), `IntradayService._on_good` (or `_on_fail`) re-appends the deleted report name back to `self.waitlist`. On the subsequent tick, `_trigger_report` registers the name into `current_runs` and calls `execute_report(name)`. `execute_report` evaluates `self.automation_service.get_by_name(name)`, finds `None`, and returns `False` immediately without registering any watcher thread or invoking `callback_good` or `callback_fail`.

**EVIDENCE**  
Lines 20–22 of `services/execution_service.py`:
```python
report = self.automation_service.get_by_name(name)
if not report:
    return False
```
Lines 243–246 of `services/intraday_service.py`:
```python
if status == Intraday.OPEN and len(self.current_runs) == 0 and len(self.waitlist) > 0:
    next_report = self.waitlist.popleft()
    self._trigger_report(next_report, today_date)
```
Lines 282–284 of `services/intraday_service.py`:
```python
def _trigger_report(self, report_name: str, date: str):
    self.current_runs[report_name] = CLOCK.formatted_now()
```
Reproduction Script: `artifacts/audits/poc/poc_f001_delete_deadlock.py`  
Run Command: `py -3 artifacts/audits/poc/poc_f001_delete_deadlock.py`  
Observed Output:
```
Initial state: current_runs=['Report_1'], waitlist=[]
After deletion: Report_1 in automations=False
After skip rotation: waitlist=['Report_1'], current_runs=[]
execute_report('Report_1') returned: False
current_runs after execute_report: ['Report_1']
len(current_runs) == 0: False
Can scheduler run new reports? False
[+] CONFIRMED F-001: Queue is permanently deadlocked with orphan in current_runs!
```

**CONSEQUENCE**  
`len(self.current_runs) == 0` evaluates to `False` on all subsequent ticks. The sequential queue stops permanently for the remainder of the calendar day. No pending or retrial reports will ever run.

**ROOT-CAUSE HYPOTHESIS**  
`delete_automation` does not check or clear `current_runs` or terminate the running process, and `execute_report` fails to clean up `current_runs` or invoke failure callbacks when an automation cannot be resolved.

**VERIFICATION CRITERION**  
Deleting an automation while it is running either terminates the process immediately or purges all references so that subsequent scheduler ticks continue processing remaining waitlist items without getting stuck in `len(current_runs) > 0`.

### F-002: Arbitrary script execution via unsanitized `dir` and `filename` in `/api/automation/add`

- **Severity:** CRITICAL
- **Confidence:** CONFIRMED
- **Category:** SECURITY
- **Invariant:** I-9
- **Location:** `controllers/automation_controller.py:add_automation:33-56`, `services/execution_service.py:execute_report:24-25`

**OBSERVATION**  
`POST /api/automation/add` extracts `dir` and `filename` from user JSON input and passes them directly to `Report(...)`. Path resolution in `ExecutionService.execute_report` uses `BASE_DIR / report.dir / report.filename` without restricting the path to an authorized directory root.

**EVIDENCE**

```python

    filename=filename,
    filetype=str(data.get("filetype") or "python").strip(),

```
Lines 24–25 of `services/execution_service.py`:
```python
script_dir = BASE_DIR / report.dir
script_path = script_dir / report.filename
```
In Python `pathlib.Path`, if `report.dir` or `report.filename` contains directory traversal sequences (`..`) or is an absolute drive path, `script_path` resolves outside `BASE_DIR`. When executed, `Runner.run_python` passes this path to `subprocess.Popen([str(self.python_exe), str(script_path)])`.

**CONSEQUENCE**  
An unauthenticated caller can register and cause the server to execute arbitrary Python or R scripts located anywhere on the host filesystem accessible by the application process.

**ROOT-CAUSE HYPOTHESIS**  
Input validation in `AutomationController.add_automation` only checks non-emptiness of `name` and `filename` and lacks canonical path resolution and directory boundary containment checks.

**VERIFICATION CRITERION**  
`POST /api/automation/add` rejects any `dir` or `filename` containing path traversal operators (`..`), absolute drive paths, or paths resolving outside the designated reports directory with HTTP 400.

### F-004: Dependency skip with non-zero exit code consumes error retry counts prematurely

- **Severity:** HIGH
- **Confidence:** CONFIRMED
- **Category:** QUEUE
- **Invariant:** I-2
- **Location:** `services/runner.py:_watcher:75-78`, `services/intraday_service.py:_on_fail:335-356`, `reports/0base_auto.py:120-126`, `models/report_log.py:parse_output:31-38`

**OBSERVATION**  
When external automation scripts such as `reports/0base_auto.py` encounter an unready dependency, they dump `status=Retrial` via `ParadisoDump()` and terminate with exit code `1`. `Runner._watcher` branches strictly on `process.returncode == 0`, dispatching non-zero exit codes to `callback_fail`. `IntradayService._on_fail` unconditionally increments `self.retry_counts[name]` without reading `ReportLog` or checking stdout/stderr for dependency skip indicators.  
Additionally, `ReportLog.parse_output` treats any stdout string containing `"NOT FOUND"` as `Skipped`. A script that exits 0 but prints messages containing "not found" (e.g., `"User profile not found in cache; created new record"`) is misclassified as `Skipped`, causing it to be marked `Retrial` and rotated repeatedly without incrementing error retries.

**EVIDENCE**  
Lines 120–126 of `reports/0base_auto.py`:
```python
except Exception as exc:
    print(f"Error during auto_read: {exc}")
    ParadisoDump().dump(
        status=ParadisoConstants.RETRIAL,
        name="0base_auto.py",
        last_output='Unavailable',
        log=str(exc)
    )
    return 1
```
Lines 75–78 of `services/runner.py`:
```python
if process.returncode == 0:
    callback_good(duration_str, output_snippet)
else:
    callback_fail(duration_str, f"Return code {process.returncode}: {output_snippet}")
```
Lines 338–340 of `services/intraday_service.py`:
```python
attempts = self.retry_counts.get(name, 0) + 1
self.retry_counts[name] = attempts
```
Lines 34–35 of `models/report_log.py`:
```python
if "SKIPPED" in txt or "MISSING DEPENDENCY" in txt or "DEPENDENCY NOT READY" in txt or "NOT FOUND" in txt:
    return "Skipped"
```
Reproduction Script: `artifacts/audits/poc/poc_f004_dep_skip_exit1.py`  
Run Command: `py -3 artifacts/audits/poc/poc_f004_dep_skip_exit1.py`  
Observed Output:
```
Cycle 1: attempts=1, status=Retrial
Cycle 2: attempts=2, status=Retrial
Cycle 3: attempts=3, status=Failed
Final status: Failed
Is still queued in waitlist: False
[+] CONFIRMED F-004: Missing dependency with exit code 1 consumed max retries and terminally failed!
```

**CONSEQUENCE**  
Scripts following the repository's sample pattern (`0base_auto.py`) that exit 1 on missing dependencies are penalized as genuine execution crashes and are permanently marked `Failed` after 3 checks, violating Invariant I-2. Conversely, reports with benign stdout containing "not found" never record completion.

**ROOT-CAUSE HYPOTHESIS**  
`_watcher` couples process exit code directly to error accounting without cross-referencing written `ReportLog` artifacts, while `ReportLog.parse_output` uses overly broad keyword heuristics.

**VERIFICATION CRITERION**  
A report signaling a missing dependency via log metadata or standard output does not increment `retry_counts` regardless of whether its process exits 0 or non-zero, and scripts exiting 0 with benign text containing "not found" are recorded as `Completed`.

### F-005: Unbounded fast-spinning and timeline write amplification when all queued reports wait on dependencies

- **Severity:** HIGH
- **Confidence:** PROBABLE
- **Category:** QUEUE
- **Invariant:** I-2, I-6
- **Location:** `services/intraday_service.py:tick:243-246`, `services/intraday_service.py:_on_good:317-334`

**OBSERVATION**  
When all reports in `self.waitlist` wait on external dependencies, each report immediately exits with a dependency skip. `_on_good` appends the report to the back of `waitlist`, writes to `logs/`, writes to `automations.json`, and appends an event to `intraday.json`. On the next tick (0.5 seconds later, or immediately if process execution is fast), the next report is popped, executed, and rotated. There is no backoff, cooldown, or full-cycle rotation detection.

**EVIDENCE**  
In `IntradayService`:
```python
if status == Intraday.OPEN and len(self.current_runs) == 0 and len(self.waitlist) > 0:
    next_report = self.waitlist.popleft()
    self._trigger_report(next_report, today_date)
```
In `_on_good`:
```python
self.waitlist.append(name)
...
self.intraday_repo.add_timeline_event(
    date=date,
    title=f"Rotated {name}",
    description=desc,
    event_type="system"
)
```
Each `add_timeline_event` calls `StorageBase.mutate()`, which acquires `_global_lock`, re-reads `intraday.json`, appends the event, and writes the entire JSON file back to disk via `os.replace()`. At 0.5s ticks, 2 dependency-blocked scripts rotate 120 times per minute, generating 7,200 rotations, 7,200 timeline events, and 14,400 atomic disk write transactions per hour.

**CONSEQUENCE**  
Severe disk I/O thrashing, rapid timeline event pollution, memory growth in `IntradayDay.timeline`, and degraded HTTP API responsiveness while waiting on file locks.

**ROOT-CAUSE HYPOTHESIS**  
`IntradayService` lacks cycle tracking or waitlist rotation throttling to pause popping when an entire queue pass yields zero completions.

**VERIFICATION CRITERION**  
When all queued items rotate without completing, the scheduler throttles re-execution and caps timeline event generation until a configured polling cooldown expires.

### F-006: Process watcher suppression vulnerability due to CPython `id(process)` memory address reuse

- **Severity:** HIGH
- **Confidence:** PROBABLE
- **Category:** CONCURRENCY
- **Invariant:** I-5, I-8
- **Location:** `services/runner.py:kill_all:44-53`, `services/runner.py:_watcher:57-69`

**OBSERVATION**  
`Runner.kill_all()` tracks killed processes by inserting `id(process)` into `self.killed_process_ids`. In CPython, `id(obj)` returns the object's memory address. When a killed process terminates and its `Popen` object is garbage collected, a subsequently spawned `Popen` object can be allocated the identical memory address.

**EVIDENCE**  
Lines 46–47 of `services/runner.py`:
```python
self.killed_processes.add(name)
self.killed_process_ids.add(id(process))
```
Lines 62–69 of `services/runner.py`:
```python
was_killed = id(process) in self.killed_process_ids or (name in self.killed_processes and self.active_processes.get(name) is not process)
self.killed_process_ids.discard(id(process))
...
if was_killed:
    return
```
If process A is killed, its PID terminates, and `Popen` reference drops. Process B is launched shortly after. The Python memory allocator assigns process B the memory address previously used by process A. When process B finishes, `id(process) in self.killed_process_ids` evaluates to `True`. `_watcher` returns without invoking `callback_good` or `callback_fail`.

**CONSEQUENCE**  
A legitimate execution of a newly launched report has its completion callback suppressed. The report remains in `current_runs` indefinitely, stalling the sequential queue.

**ROOT-CAUSE HYPOTHESIS**  
Object memory addresses (`id()`) are transient and subject to heap reuse in Python; they are unsafe as unique process lifecycle tokens.

**VERIFICATION CRITERION**  
Killed process tracking uses immutable, monotonically increasing launch identifiers or UUIDs that cannot collide across object allocations.

### F-008: Child process trees survive `Runner.kill_all()` on Windows

- **Severity:** MEDIUM
- **Confidence:** CONFIRMED
- **Category:** PROCESS
- **Invariant:** I-5
- **Location:** `services/runner.py:kill_all:42-53`

**OBSERVATION**  
`Runner.kill_all()` iterates over active processes and calls `process.terminate()` followed by `process.kill()`. On Windows, standard library `Popen.kill()` terminates only the root process. Any child processes spawned by the Python or R script (e.g., worker pools, database drivers, external tools) continue running in the background.

**EVIDENCE**  
Lines 49–50 of `services/runner.py`:
```python
process.terminate()
process.kill()
```
On Windows, `TerminateProcess` operates strictly on the specific process handle without cascading down the process tree.  
Reproduction Script: `artifacts/audits/poc/poc_f008_orphan_process_tree.py`  
Run Command: `py -3 artifacts/audits/poc/poc_f008_orphan_process_tree.py`  
Observed Output:
```
Parent PID: 30564, Spawned Child PID: 34684
Invoking runner.kill_all()...
Parent dead: True
Child PID 34684 survived kill_all(): True
[+] CONFIRMED F-008: Child process trees survive Runner.kill_all() on Windows!
```

**CONSEQUENCE**  
Orphan processes remain active after scheduler stop, test reset, or 10:00 PM cutoff, retaining file locks and consuming CPU/memory.

**ROOT-CAUSE HYPOTHESIS**  
`kill_all()` relies solely on `Popen.kill()` rather than tree-aware termination mechanisms (such as `taskkill /F /T /PID` or `psutil.Process.children()`).

**VERIFICATION CRITERION**  
Invoking `kill_all()` terminates both the immediate process and all descendant processes spawned by it.

### F-009: Concurrent `POST /api/paradiso/start` invocations spawn duplicate scheduler loops

- **Severity:** MEDIUM
- **Confidence:** PROBABLE
- **Category:** CONCURRENCY
- **Invariant:** I-1, I-11
- **Location:** `services/paradiso.py:start:45-52`

**OBSERVATION**  
`Paradiso.start()` inspects `self.is_running()` and then instantiates and starts a new thread. `Paradiso` possesses no synchronization lock guarding `start()` and `stop()`.

**EVIDENCE**  
Lines 45–52 of `services/paradiso.py`:
```python
def start(self) -> bool:
    self.intraday_service.start_fresh_run()
    if self.is_running():
        return True
    self._stop_event.clear()
    self._thread = threading.Thread(target=self._loop, daemon=True)
    self._thread.start()
    return True
```
If two HTTP requests arrive concurrently at `POST /api/paradiso/start`, both can evaluate `self.is_running()` as `False` before either thread assigns `self._thread`. Both spawn separate daemon threads executing `self._loop`.

**CONSEQUENCE**  
Multiple concurrent scheduler threads execute `tick()` simultaneously, doubling polling overhead and increasing lock contention.

**ROOT-CAUSE HYPOTHESIS**  
`Paradiso` scheduler lifecycle operations lack mutual exclusion.

**VERIFICATION CRITERION**  
Concurrent calls to `start()` result in strictly one active background scheduler thread.

### F-010: Midnight rollover resets running reports and duplicates queue entries

- **Severity:** MEDIUM
- **Confidence:** PROBABLE
- **Category:** STATE-MACHINE
- **Invariant:** I-4, I-8
- **Location:** `services/intraday_service.py:tick:191-224`

**OBSERVATION**  
When the date advances across midnight while a report is actively running in `current_runs`, `day` for the new date is `None`. `tick()` executes `automation_service.set_waiting_all()`, resetting all report statuses in `automations.json` to `Waiting`, including the report currently executing. The report is added to the new day's `self.waitlist`.

**EVIDENCE**  
Lines 196–211 of `services/intraday_service.py`:
```python
waiting = self.automation_service.set_waiting_all()
day = IntradayDay(...)
self.intraday_repo.add_day(day)
if self.is_active:
    self.waitlist = deque(waiting)
```
When the in-flight process finishes, its completion callback updates `automations.json` with status `Completed` (or appends to `waitlist` if skipped). However, the new day's `waitlist` already contains the report. If skipped, `waitlist` now contains duplicate entries for the same report.

**CONSEQUENCE**  
A report executing across midnight can end up duplicated in the queue or marked `Completed` while still present in today's `waitlist`.

**ROOT-CAUSE HYPOTHESIS**  
Midnight rollover does not check or drain `current_runs` before re-initializing `automations.json` and constructing the new day's queue.

**VERIFICATION CRITERION**  
Crossing midnight with an in-flight job cleanly finalizes the job before constructing the new daily queue without duplicate entries.

### F-011: 1-second unpaginated timeline polling and hardcoded dashboard countdown

`app.js` runs a 1000ms polling interval firing 4 requests every second: `/api/dashboard/stats`, `/api/automations`, `/api/dashboard/timeline`, and `/api/paradiso/status`. `/api/dashboard/timeline` returns the entire daily timeline in a single unpaginated payload. ## 4. REFUTED HYPOTHESES

1. **Storage mutation lost updates under concurrency**:  
   *Hypothesis:* Concurrent calls to `mutate()` across threads lose updates.  
   *Result:* Refuted. `StorageBase._global_lock` is a reentrant lock held across read, mutation, and `os.replace()`, preventing lost updates. Verified by passing test `test_storage_base_concurrent_mutations_no_lost_updates`.

2. **Manual execution bypass via `/api/automation/run`**:  
   *Hypothesis:* Manual triggers can bypass sequential execution.  
   *Result:* Refuted. `ExecutionController.run_automation()` unconditionally returns HTTP 403 Forbidden.

3. **Log viewer path traversal (`/api/executions/log/<name>`)**:  
   *Hypothesis:* URL traversal characters can read arbitrary system files.  
   *Result:* Refuted. `ExecutionController.get_execution_log()` validates `safe_name == name`, rejects `..`, `/`, `\`, and asserts `is_relative_to(logs_dir)`.

4. **Secret key exposure in `/api/settings`**:  
   *Hypothesis:* Secret keys leak in plain text over GET requests.  
   *Result:* Refuted. `get_sanitized_config()` masks `secret_key` with `••••••••`, and `save_config()` ignores the placeholder on save.
