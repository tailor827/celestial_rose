### Finding F-061: Mid-Pass Cross-Lane Completion (`wake_lane_a_queue()`) Fails to Prevent End-of-Pass Starvation Cooldown and Leaves Pre-Wakeup Skipped `P0` Reports Marked as Seen

#### 1. Observation
Under Milestone `P3.2`, [`IntradayService.wake_lane_a_queue()`](file:///c:/Users/desktop/Documents/work/celestial_rose/paradiso/services/intraday_service.py#L119-L124) is invoked when a Lane B recurring report completes ([line 1078](file:///c:/Users/desktop/Documents/work/celestial_rose/paradiso/services/intraday_service.py#L1078)) or a Lane C timeslot report completes ([line 1203](file:///c:/Users/desktop/Documents/work/celestial_rose/paradiso/services/intraday_service.py#L1203)):
```python
def wake_lane_a_queue(self):
    """P3.2: Event-driven wakeup — resets adaptive starvation backoff and clears active cooldown."""
    with self._lock:
        self._consecutive_starvation_passes = 0
        self._rotation_cooldown_until = 0.0
```
However, `wake_lane_a_queue()` only clears `_rotation_cooldown_until = 0.0` and `_consecutive_starvation_passes = 0` at the moment it is called. When a Lane B or Lane C dependency finishes **mid-pass** (after a `P0` Lane A report has already skipped on that dependency in the current pass, while lower-priority `P1`/`P2` Lane A reports in the same pass have not yet finished):
1. The pre-wakeup skipped `P0` report remains in `self._cycle_seen_in_pass`, so `tick()` refuses to re-evaluate `P0` until all lower-priority `P1`/`P2` reports in the pass have run.
2. When the remaining `P1`/`P2` reports in the pass subsequently skip on their own unready dependencies, [`_evaluate_pass_completion()`](file:///c:/Users/desktop/Documents/work/celestial_rose/paradiso/services/intraday_service.py#L169-L173) checks:
   ```python
   if self._cycle_skips_in_pass > 0 and self._cycle_completions_in_pass == 0 and self._cycle_errors_in_pass == 0 and len(self.waitlist) > 0:
       self._consecutive_starvation_passes += 1
       cooldown = self.get_adaptive_rotation_cooldown()
       self._rotation_cooldown_until = time.time() + cooldown
   ```
   Because `self._cycle_completions_in_pass` only tracks **Lane A** completions (`0`), `_evaluate_pass_completion()` treats the pass as a pure starvation pass and **engages a 30-second starvation cooldown**, completely erasing the mid-pass `wake_lane_a_queue()` wakeup!

#### 2. Evidence
1. Consider a Lane A pass containing `Rep_P0_Needs_B` (`P0`, waiting on Lane B's `Feed_B`) and `Rep_P2_Needs_Missing` (`P2`, waiting on an unready external table):
   - **Step 1:** `Rep_P0_Needs_B` runs and skips (`DEPENDENCY_UNREADY` because `Feed_B` is still running). `_cycle_seen_in_pass = {'Rep_P0_Needs_B'}`, `_cycle_skips_in_pass = 1`, `waitlist = ['Rep_P2_Needs_Missing', 'Rep_P0_Needs_B']`.
   - **Step 2:** `Feed_B` completes in Lane B (`_trigger_type_b_report._on_good`) and calls `self.wake_lane_a_queue()`. At this moment `_rotation_cooldown_until` is already `0.0`, and `_cycle_seen_in_pass` is untouched (`{'Rep_P0_Needs_B'}`).
   - **Step 3:** On the next `tick()`, `Rep_P0_Needs_B` is filtered out of `unseen_candidates` because it is still in `_cycle_seen_in_pass`. `Rep_P2_Needs_Missing` is dispatched instead and skips (`_cycle_skips_in_pass = 2`).
   - **Step 4:** `_evaluate_pass_completion()` sees `_cycle_skips_in_pass == 2` and `_cycle_completions_in_pass == 0`, increments `_consecutive_starvation_passes = 1`, and locks Lane A into a **30-second starvation cooldown** (`_rotation_cooldown_until = now + 30.0`), even though `Feed_B` completed during the pass and `Rep_P0_Needs_B` is ready to run immediately!
2. **Reproduced in Sandbox:** Running `poc_f061_f065_audit_batch14.py` (`test_f061_mid_pass_cross_lane_completion_prevents_cooldown_and_wakes_p0`) fails with:
   ```
   AssertionError: 1790998585.2908294 != 0.0 : F-061: Lane A entered starvation cooldown (until=1790998585.2908294) despite Feed_B completing mid-pass!
   ```

#### 3. Consequence
- Violates Invariants `I-1` (Priority-FIFO ordering `P0 -> P1 -> P2`), `I-2` (Adaptive Starvation Cooldown & Event-Driven Wakeup), and `I-8` (Queue / Memory State Convergence).
- Cross-lane completions (`Lane B` or `Lane C`) that occur while a Lane A pass is partially complete fail to wake previously skipped `P0` reports and fail to prevent Lane A from entering a 30-second starvation cooldown at the end of the pass.

#### 4. Verification Criterion
1. When `wake_lane_a_queue()` is invoked mid-pass (e.g., upon a Lane B or Lane C completion, or report registration/re-enablement), any Lane A reports that were already marked as seen (`_cycle_seen_in_pass`) before the wakeup event MUST be eligible for re-evaluation in priority order without Lane A entering a starvation cooldown at the conclusion of the pass.
2. `test_f061_mid_pass_cross_lane_completion_prevents_cooldown_and_wakes_p0` in `poc_f061_f065_audit_batch14.py` MUST pass.

### Finding F-062: Unvalidated Settings Parameters (`max_retries`, `max_rotation_cooldown_seconds`, and `null` Scheduler Fields) in `validate_config()` Allow Disk Config Corruption, `HTTP 500` Crashes, and Complete Lane B / Cooldown Paralysis

#### 1. Observation
In [`SettingsController.update_settings()`](file:///c:/Users/desktop/Documents/work/celestial_rose/paradiso/controllers/settings_controller.py#L61-L65), `save_config(new_settings)` is executed **before** `self.intraday_service.reload_config(updated_cfg)`:
```python
updated_cfg = save_config(new_settings)
if self.intraday_service:
    self.intraday_service.reload_config(updated_cfg)
```
Inside [`save_config()`](file:///c:/Users/desktop/Documents/work/celestial_rose/paradiso/utils/config.py#L142-L178), `validate_config(merged)` is called first, and if it returns no errors, `merged` is **immediately written to `config.yaml` on disk and mutated into global `CONFIG`** before `reload_config()` runs.

However, [`validate_config()`](file:///c:/Users/desktop/Documents/work/celestial_rose/paradiso/utils/config.py#L23-L118) completely omits validation for `scheduler.max_retries` and `scheduler.max_rotation_cooldown_seconds`, and uses `is not None` guards (`if val is not None:`) that allow explicit JSON `null` (`None`) values for critical scheduler fields to bypass validation and overwrite defaults in `merged` via `_deep_merge()`.

   - Submitting `POST /api/settings` with `{"scheduler": {"max_retries": 0}}` (or `-1`) passes `validate_config()` and returns `HTTP 200 OK`, setting `self.intraday_service.max_retries = 0`. On the very next `tick()`, Lane B evaluates ([`intraday_service.py:725`](file:///c:/Users/desktop/Documents/work/celestial_rose/paradiso/services/intraday_service.py#L725)):


   - Submitting `{"scheduler": {"max_retries": "not_an_int"}}` passes `validate_config()`, **writes `"not_an_int"` to `config.yaml` on disk and `CONFIG` in memory**, and only then throws an unhandled `ValueError` in `reload_config()` (`int("not_an_int")`), returning `HTTP 500` while leaving `config.yaml` permanently corrupted on disk.
2. **Unvalidated `scheduler.max_rotation_cooldown_seconds` (`<= 0` or non-numeric string):**

   - Submitting `{"scheduler": {"lane_c_catch_up_grace_minutes": null}}` passes `validate_config()`, writes `null` to `config.yaml`, and crashes `reload_config()` at `int(sched.get("lane_c_catch_up_grace_minutes", 30))` (`int(None)` -> `TypeError`, `HTTP 500`).

4. **Reproduced in Sandbox:** Running `poc_f061_f065_audit_batch14.py` (`test_f062_settings_validation_prevents_invalid_max_retries_cooldown_and_nulls`) fails on the first vector (`200 != 400 : F-062: max_retries=0 accepted with 200`) and reproduces all sub-vectors.

### Finding F-063: Substring Check `"cutoff" in str(reason).lower()` in `_get_completed_or_exhausted_reports()` Misclassifies Genuine Script Failures Mentioning `"cutoff"`, Causing Infinite Re-Execution and Cooldown Destruction

#### 1. Observation
In [`IntradayService._get_completed_or_exhausted_reports()`](file:///c:/Users/desktop/Documents/work/celestial_rose/paradiso/services/intraday_service.py#L309-L316), the engine determines which reports in `day.reports_ran` have already completed or permanently exhausted their retry budget today:
```python
for r_name, r_info in day.reports_ran.items():
    if isinstance(r_info, dict):
        reason = r_info.get("reason")
        if not reason or "Dependency" in str(reason) or "cutoff" in str(reason).lower():
            continue
    done.add(r_name)
```
Meanwhile, [`Automations.get_pending_by_type("type_a")`](file:///c:/Users/desktop/Documents/work/celestial_rose/paradiso/models/automation.py#L70) returns all Type A reports whose status is `not in ["Completed", "Disabled"]` — which **includes reports in `"Failed"` status**.

In [`IntradayService.tick()`](file:///c:/Users/desktop/Documents/work/celestial_rose/paradiso/services/intraday_service.py#L687-L695), any report returned by `get_pending_by_type("type_a")` that is not in `already_ran` (`_get_completed_or_exhausted_reports(day)`) is treated as newly uncompleted, triggers `self.wake_lane_a_queue()`, and is re-enqueued into `self.waitlist`!

Because line 312 checks `or "cutoff" in str(reason).lower()` across the entire `reason` string without distinguishing system cutoff terminations (`"Terminated due to 22:00 cutoff"`) from retry-exhausted script failures (`"Exceeded max retries (3/3): ..."`), **any report whose error message contains the substring `"cutoff"` (such as `"SQL Error: missing EOD cutoff timestamp in ledger"`, `"Cutoff validation failed"`, etc.) is excluded from `already_ran` even after exhausting `max_retries` and transitioning to `"Failed"`!**

#### 2. Evidence
1. When a Lane A report (`Rep_Cutoff_Error`) fails `max_retries` times (`2/2`) with `"SQL Error: missing EOD cutoff timestamp in ledger table"`, [`_trigger_report._handle_failure`](file:///c:/Users/desktop/Documents/work/celestial_rose/paradiso/services/intraday_service.py#L995-L999) records:
   - `automations.json`: `status = "Failed"`
   - `intraday.json` (`day.reports_ran["Rep_Cutoff_Error"]`): `reason = "Exceeded max retries (2/2): SQL Error: missing EOD cutoff timestamp in ledger table"`
2. On the very next `tick()`:
   - `_get_completed_or_exhausted_reports(day)` inspects `reason`, matches `"cutoff" in str(reason).lower()`, and skips adding `"Rep_Cutoff_Error"` to `done`.
   - `tick()` (lines 687–695) sees `"Rep_Cutoff_Error"` in `get_pending_by_type("type_a")` and not in `already_ran`, calls `self.wake_lane_a_queue()` (destroying any active starvation cooldown for other reports), re-enqueues `"Rep_Cutoff_Error"` into `self.waitlist`, and dispatches it again (`attempt 3/2`, `4/2`, `5/2`, ... in an unbounded infinite loop)!
3. Similarly, in Lane C, [`_hydrate_type_c_ran_today()`](file:///c:/Users/desktop/Documents/work/celestial_rose/paradiso/services/intraday_service.py#L304) calls `_get_completed_or_exhausted_reports(day)`, so a permanently failed Lane C report whose error mentions `"cutoff"` is not hydrated into `type_c_ran_today` upon restart.
4. **Reproduced in Sandbox:** Running `poc_f061_f065_audit_batch14.py` (`test_f063_failed_report_with_cutoff_in_error_message_does_not_loop_infinitely`) fails with:
   ```
   AssertionError: 4 != 2 : F-063: Permanently failed report with 'cutoff' in error message ran 4 times (expected max_retries=2)!
   ```

#### 3. Consequence
- Violates Invariants `I-1` (Single-Flight & Exhaustion Termination), `I-2` (Max Retries Cap & Starvation Cooldown), `I-6` (Storage State Integrity), and `I-8` (Queue / Storage / Memory Convergence).

#### 4. Verification Criterion

A report that has exhausted its retry budget (`status == "Failed"` / `"Exceeded max retries"`) MUST be recognized as exhausted by `_get_completed_or_exhausted_reports(day)` and MUST NOT be re-enqueued into `waitlist` by `tick()`, regardless of whether the script's error output contains the word `"cutoff"` or `"Dependency"`.

### Finding F-064: Pre-Start Timeline Events (`disable`, `enable`, or Manual `run`) on a New Day Create an Uninitialized Day Record in `intraday.json`, Causing `_get_or_init_day()` to Skip `set_waiting_all()` and Starve All Prior-Day Completed Reports (Plus `start_lane()` Omitting Crashed `"Running"` Report Recovery)

#### 1. Observation

1. **Pre-Start Timeline Event Poisons `_get_or_init_day()` on a New Day:**
   When Paradiso boots on a new calendar day in Standby Mode (all lanes stopped), `automations.json` still holds yesterday's final report statuses (`status: "Completed"` for reports that succeeded yesterday), while `intraday.json` does not yet have an entry for `today_date`.

   ```python
           "status": "OPEN",
           "expected_reports": [],
           "reports_ran": {},
           "timeline": [],
       }
   ```
   When the operator then starts Lane A, B, or C via `POST /api/paradiso/lane/start` (`start_lane()`) or `POST /api/paradiso/start` (`start_fresh_run()`), [`_get_or_init_day(today_date, status="OPEN")`](file:///c:/Users/desktop/Documents/work/celestial_rose/paradiso/services/intraday_service.py#L319-L357) inspects `intraday.json`:

2. **`start_lane()` Omits Crashed `"Running"` -> `"Waiting"` Recovery:**

### Finding F-065: Manual Execution (`POST /api/automation/run`) of a Lane B or Lane C Report While Its Lane Is in Standby Permanently Fails on Attempt `1 / max_retries` With `"Exceeded max retries (1/N)"`

#### 1. Observation
By design ([`ExecutionController.run_automation()`](file:///c:/Users/desktop/Documents/work/celestial_rose/paradiso/controllers/execution_controller.py#L41-L65)), Type B and Type C reports support on-demand manual execution via `POST /api/automation/run` during `OPEN` hours even when `lane_b_active` or `lane_c_active` is `False` (Standby Mode).

However, inside [`IntradayService._trigger_type_b_report._handle_failure`](file:///c:/Users/desktop/Documents/work/celestial_rose/paradiso/services/intraday_service.py#L1112-L1139) and [`_trigger_type_c_report._handle_failure`](file:///c:/Users/desktop/Documents/work/celestial_rose/paradiso/services/intraday_service.py#L1238-L1265), the failure handler checks:
```python
attempts = self.retry_counts.get(name, 0) + 1
self.retry_counts[name] = attempts
scheduler_is_active = self.lane_b_active or self.force_open  # (or self.lane_c_active or self.force_open)
if attempts < self.max_retries and scheduler_is_active:
    # Retrial branch (attempts < max_retries)
    ...
else:
    # Terminal Failed branch!
    self.type_b_exhausted.add(name)  # (or self.type_c_ran_today.add(name))
    self.automation_service.update_status(
        name, "Failed", last_run=now_str,
        last_output=f"Exceeded max retries ({attempts}/{self.max_retries}): {reason_str}"
    )
```
When an operator triggers a manual run of a Lane B or Lane C report while its lane is in Standby (`lane_b_active == False`, `force_open == False`), `scheduler_is_active` is `False`. If the script encounters a single transient error on **attempt `1` of `5`** (`attempts = 1`, `max_retries = 5`), `if attempts < self.max_retries and scheduler_is_active:` evaluates to `False` and execution jumps straight into the terminal `else:` branch!

#### 2. Evidence
1. On attempt `1` (`attempts = 1`, `self.max_retries = 5`):
   - The report is immediately marked with `status = "Failed"` and a contradictory `last_output`:
     `"Exceeded max retries (1/5): Transient network timeout"`
   - For Lane B, `name` is added to `self.type_b_exhausted`. For Lane C, `name` is added to `self.type_c_ran_today` and recorded in `day.reports_ran` with `"Exceeded max retries (1/5): ..."`.
   - Because of the `F-043` guard (`if report.status == "Failed" or name in self.intraday_service.type_b_exhausted: return 409`), the operator cannot even click **Run** again (`HTTP 409 Conflict`), and when the operator subsequently starts Lane B or Lane C, the scheduler permanently skips the report as exhausted for the rest of the day despite `4` remaining retry attempts (`1 < 5`)!
2. **Reproduced in Sandbox:** Running `poc_f061_f065_audit_batch14.py` (`test_f065_manual_run_while_lane_standby_does_not_permanently_fail_on_first_attempt`) fails with:
   ```
   AssertionError: 'Rep_Manual_B' unexpectedly found in {'Rep_Manual_B'} : F-065: Manual run failure on attempt 1/5 prematurely exhausted Rep_Manual_B (last_output=Exceeded max retries (1/5): Transient network timeout)!
   ```

#### 3. Consequence
- Violates Invariants `I-2` (Error Retry Budget up to `max_retries`), `I-7` (Honest API / UI Telemetry — reporting `"Exceeded max retries (1/5)"`), and `I-8` (Queue / Storage / Memory Convergence).
- A single transient failure during an on-demand manual run while a lane is in Standby prematurely exhausts the report on attempt `1/N`, blocks subsequent manual runs with `HTTP 409`, and starves autonomous execution when the lane is started.

#### 4. Verification Criterion
1. In `_trigger_type_b_report._handle_failure` and `_trigger_type_c_report._handle_failure`, a report MUST only transition to terminal `"Failed"` (`"Exceeded max retries (...)"` and `type_b_exhausted` / `type_c_ran_today`) when `attempts >= self.max_retries`. When `attempts < self.max_retries` (even if triggered manually while the lane is in standby), the report MUST enter `"Retrial"` status with its accurate attempt count (`attempts / max_retries`) rather than being permanently exhausted on attempt `1`.
2. `test_f065_manual_run_while_lane_standby_does_not_permanently_fail_on_first_attempt` in `poc_f061_f065_audit_batch14.py` MUST pass.
