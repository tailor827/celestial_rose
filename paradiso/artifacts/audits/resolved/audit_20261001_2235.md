## 3. REMEDIATION VERIFICATION DETAILS

### F-044: Cross-Lane Operating Window Override Leaks into Lane A Waitlist in `add_automation` — **RESOLVED**
- **Verification Criterion:** `AutomationController.add_automation()` must gate Type A waitlist enqueueing strictly on `self.intraday_service.lane_a_active`. If Lane A is stopped, newly registered Type A reports must NEVER be pushed into `waitlist`, regardless of the value of `force_open` or the state of other lanes.
- **Evidence:**
  - In `paradiso/controllers/automation_controller.py:add_automation:125-132`, `lane_a_active` is evaluated strictly as `bool(self.intraday_service.lane_a_active) if self.intraday_service else False`.
  - `poc_f044_lane_a_force_open_leak_in_add_automation.py` passes cleanly.
  - Unit test `test_f044_add_automation_does_not_leak_on_cross_lane_force_open` in `paradiso/tests/test_audit_fixes.py` passes without artificial `force_open = False` test overrides.

### F-045: Re-Enabled Lane C Reports Are Permanently Starved from Autonomous Dispatch — **RESOLVED**
- **Verification Criterion:** When `POST /api/automation/enable` is called on a Lane C report, the report must be evicted from `self.intraday_service.type_c_ran_today`, `self.intraday_service.type_c_retry_after`, and `self.intraday_service.type_c_warned`, allowing Lane C to autonomously dispatch the re-enabled report at its scheduled time slot.
- **Evidence:**
  - In `paradiso/controllers/automation_controller.py:enable_automation:246-251`, re-enabling a report clears `type_b_exhausted`, `type_c_ran_today`, `type_c_retry_after`, `type_c_warned`, and `retry_counts`, and invokes `self.intraday_service.intraday_repo.clear_non_completed_run(today_date, name)` (`paradiso/models/intraday.py:141-148`).
  - Clearing the non-completed run record from `day.reports_ran` ensures that `_hydrate_type_c_ran_today()` and `_get_completed_or_exhausted_reports()` do not re-hydrate the prior failed run from disk on the subsequent `tick()`.
  - `poc_f045_type_c_enable_starvation.py` and `test_f045_re_enabled_type_c_clears_ran_today_and_dispatches` pass.

### F-046: Zero-Interval Input Validation Bypass in `AutomationController.add_automation` — **RESOLVED**
- **Verification Criterion:** Submitting `interval_minutes: 0` to `POST /api/automation/add` must return HTTP 400 Bad Request with an error message stating that `interval_minutes` must be an integer >= 1.
- **Evidence:**
  - In `paradiso/controllers/automation_controller.py:add_automation:75-84`, `raw_interval = data.get("interval_minutes")` is checked explicitly against `None` before integer conversion and `< 1` bounds checking.
  - `poc_f046_zero_interval_validation_bypass.py` and `test_f046_zero_interval_rejected_with_400` pass.

### F-047: Timeslot Tier Resolution Desync Between UI Presets and Backend Scheduler — **RESOLVED**
- **Verification Criterion:** UI timeslot presets and backend tier dispatch must be strictly synchronized: (1) Preset labels and auto-filled values in `index.html` and `app.js` must match backend schedule definitions (`BOD: 07:00`, `MID: 12:00`, `EOD: 20:30`), OR (2) Backend timeslot tier evaluation must respect `rep.scheduled_time` if explicitly provided.
- **Evidence:**
  - Both criteria were implemented:
    1. `paradiso/web/templates/index.html:1639-1641` and `paradiso/web/static/js/app.js:844-854` align UI preset labels and auto-fill values to `BOD: 07:00`, `MID: 12:00`, and `EOD: 20:30`.
    2. `paradiso/services/intraday_service.py:tick:671-681` prioritizes explicit `rep.scheduled_time` when present before falling back to tier milestone defaults (`07:00`, `12:00`, `20:30`, `08:30`).
  - `poc_f047_timeslot_tier_desync.py` and `test_f047_timeslot_tier_and_scheduled_time_alignment` pass.

## 4. REFUTED HYPOTHESES (BLAST RADIUS & REGRESSION ATTACKS)

1. **Hypothesis:** Re-enabling a Failed Lane C report clears `self.type_c_ran_today` in memory, but on the very next `tick()`, `_hydrate_type_c_ran_today(today_date)` reads `day.reports_ran` from `intraday.json`, sees `result == "failed"`, and re-inserts `name` into `type_c_ran_today`, starving the report again.
   - **Result:** **REFUTED.** `enable_automation()` calls `intraday_repo.clear_non_completed_run(today_date, name)` under `self.intraday_service._lock`, which atomically removes the non-completed run entry (`result != "completed"`) from `day.reports_ran` in `intraday.json` before the next tick.
2. **Hypothesis:** Calling `clear_non_completed_run(today_date, name)` could erase a legitimate `"completed"` run record if somehow invoked on a completed report.
   - **Result:** **REFUTED.** `enable_automation()` rejects reports whose status is not in `("Disabled", "Failed")` with HTTP 400, and `clear_non_completed_run()` explicitly guards `if existing and existing.get("result") != "completed":`.
3. **Hypothesis:** Re-enabling a Failed Lane A report while Lane A is in starvation cooldown (`_rotation_cooldown_until > time.time()`) leaves the queue paused until cooldown expiry.
   - **Result:** **REFUTED.** `enable_automation()` resets `self.intraday_service._rotation_cooldown_until = 0.0`, sets `self.intraday_service.all_completed = False`, and registers `name` in `_cycle_pass_reports`.
