## 3. Deep-Dive Vulnerability Dossier

### F-032: `_has_completed_runs` Heuristic Causes Queue Paralysis on Partial Days and Cleanses Genuine Outage Logs

- **Severity:** CRITICAL
- **Invariants Breached:** I-4, I-6, I-8
- **Source Location:** `paradiso/services/intraday_service.py:_get_or_init_day:208-216, 232-235`
- **Adversarial Asset:** `paradiso/artifacts/audits/poc/poc_f032_partial_day_paralysis.py`

**OBSERVATION**  
To remediate the fragile string matching identified in the prior audit, DEV replaced the reason string check with:
```python
def _has_completed_runs(self, day: Optional[IntradayDay]) -> bool:
    return any(
        (getattr(r, "result", None) or (r.get("result") if isinstance(r, dict) else "")) == "completed"
        for r in day.reports_ran.values()
    )
```
and conditioned day record cleansing upon:
```python
elif (status == Intraday.OPEN or force_open) and day.status == Intraday.CLOSED:
    if not self._has_completed_runs(day):
        is_stale_or_premature = True
```

**EVIDENCE**  
Demonstrated deterministically in `poc_f032_partial_day_paralysis.py`.  
When a day record is prematurely closed or the daemon restarts mid-day after a single report has completed successfully (e.g. `Report_1` completed, while `Report_2` and `Report_3` are marked failed with `"Not completed before 10:00 PM cutoff"`):
1. `_has_completed_runs(day)` evaluates to `True`.
2. `is_stale_or_premature` evaluates to `False`. The day record is **not cleansed**.
3. `start_lane("type_a")` executes `already_ran = set(day.reports_ran.keys())`. `already_ran` contains `Report_1`, `Report_2`, and `Report_3`.
4. `queue_items = [r for r in pending if r not in already_ran and r not in self.current_runs]`.
5. `self.waitlist` has length `0`.
6. `Report_2` and `Report_3` are never queued and never executed.

Conversely, if a morning outage causes 3 reports to fail genuine executions after 3 retries (0 completed), restarting the service sees `_has_completed_runs(day) == False`. It marks `is_stale_or_premature = True` and **wipes `reports_ran = {}`**, deleting genuine audit logs from disk.

**CONSEQUENCE**  
On any day where at least one report succeeded prior to a service interruption or premature closure, all remaining uncompleted reports are permanently locked out of execution for the remainder of the day (total queue paralysis). If no report completed during an outage, restarting the service destroys historical failure logs.

**VERIFICATION CRITERION**  
The waitlist generation logic must not use an all-or-nothing day cleansing check based on whether any report completed. Reports that were terminated due to premature cutoffs or that have not completed successfully or exhausted genuine retries must be enqueued into `waitlist` without erasing the historical execution records of completed or genuinely failed runs.

### F-035: Cold Boot Hydration of Time-Only `last_run` Synthesizes Future Timestamp, Permanently Suppressing Lane B

- **Severity:** CRITICAL
- **Invariants Breached:** I-1, I-4, Lane B Recurring Dispatch Invariant
- **Source Location:** `paradiso/services/intraday_service.py:_hydrate_type_b_last_run:192-195`, `_parse_timestamp:162-177`
- **Adversarial Asset:** `paradiso/artifacts/audits/poc/poc_f035_lane_b_cold_boot_suppression.py`

**OBSERVATION**  
In `_hydrate_type_b_last_run()`, lines 192–195 fall back to `rep.last_run` in `automations.json`:
```python
if not parsed_dt and rep.last_run and rep.last_run != "--":
    parsed_dt = self._parse_timestamp(rep.last_run, date)
```
When `rep.last_run` is stored as a time string without a full calendar date (e.g. `"09:30:00 PM"` from yesterday evening), `_parse_timestamp()` executes lines 172–174:
```python
base_dt = datetime.strptime(today_date, "%Y%m%d")
return datetime.combine(base_dt.date(), t)
```
This binds yesterday's execution time to *today's date*.

**EVIDENCE**  
Demonstrated deterministically in `poc_f035_lane_b_cold_boot_suppression.py`.  
When booting at 08:00 AM on 2026-09-28 with `last_run: "09:30:00 PM"` in `automations.json`:
1. `parsed_dt` is hydrated as `2026-09-28 21:30:00` (13.5 hours in the future).
2. In `tick()`:
   ```python
   elapsed = (CLOCK.now() - last_run).total_seconds()
   ```
   `elapsed` evaluates to a large negative number ($\approx -48600$s).
3. The condition `elapsed >= interval_sec` evaluates to `False`.
4. `self._trigger_type_b_report` is never invoked during the business day.

**CONSEQUENCE**  
Recurring Lane B pipelines are completely silenced and will not dispatch on any day following a morning restart or deployment whenever `automations.json` contains time-formatted execution logs from the previous evening.

**VERIFICATION CRITERION**  
Hydration of `type_b_last_run` on cold boot must never construct timestamps in the future. Any catalog `last_run` string that does not include an explicit calendar date matching `CLOCK.date_str()` must either be rejected or recognized as historical so that recurring interval evaluation proceeds immediately upon startup.

### F-033: `force_open` Stickiness Eliminates `WAITING_TO_CLOSE` Wrap-Up Window and Leaks Out-of-Window Permission Cross-Lane

- **Severity:** HIGH
- **Invariants Breached:** I-3, I-7
- **Source Location:** `paradiso/services/intraday_service.py:resolve_status:266-267`, `paradiso/controllers/paradiso_controller.py:lane_start:68-73`
- **Adversarial Asset:** `paradiso/artifacts/audits/poc/poc_f033_waiting_to_close_and_cross_lane_leak.py`

**OBSERVATION**  
While DEV enforced `t >= self.close_time -> CLOSED` ahead of `force_open`, `self.force_open` remains `True` across the entire operational lifecycle until all lanes are stopped or 22:00 is reached.  
1. Between 21:00 and 21:59 (`WAITING_TO_CLOSE`), `resolve_status()` checks `if self.force_open: return Intraday.OPEN`. The status resolves as `OPEN` instead of `WAITING_TO_CLOSE`.
2. `force_open` is maintained as a single global flag on `IntradayService`. In `ParadisoController.lane_start()`:
```python
status = self.paradiso.intraday_service.resolve_status()
if status != "OPEN" and not force_open and not getattr(self.paradiso.intraday_service, "force_open", False):
    return 409
```
Because `resolve_status()` returns `OPEN` and `self.force_open` is `True`, any other lane can be started without providing `force_open: true`.

**EVIDENCE**  
Demonstrated deterministically in `poc_f033_waiting_to_close_and_cross_lane_leak.py`.  
When Lane A is started with `force_open=True`:
1. At 21:15, `resolve_status()` returns `"OPEN"`. The evening wrap-up grace period is eliminated, and new jobs continue to pop and dispatch until 21:59:59.
2. A request to `POST /api/paradiso/lane/start` with payload `{"lane": "type_b"}` (omitting `force_open`) returns HTTP 200 OK outside the open window.

**CONSEQUENCE**  
The bank-mandated 21:00–21:59 quiet wrap-up period is completely suppressed whenever any lane was forced open. Furthermore, out-of-window permission leaks across lane boundaries, violating independent lane control isolation.

**VERIFICATION CRITERION**  
`force_open` overrides must not suppress the `WAITING_TO_CLOSE` state transition once operational hours reach 21:00, and forcing one lane open must not permit other lanes to start out-of-window without explicit per-lane authorization.

### F-036: Asymmetric Automation Disabling API Without Re-enable Capability Forces Destructive Queue Wipes

- **Severity:** MEDIUM
- **Invariants Breached:** I-7, I-8
- **Source Location:** `paradiso/controllers/automation_controller.py:16-20`, `paradiso/services/automation_service.py`

**OBSERVATION**  
In implementing hardening V-01, DEV added `POST /api/automation/disable` to allow disabling idle automations. However, no corresponding `POST /api/automation/enable` endpoint was created in `AutomationController`, and `AutomationService` exposes no single-automation enablement method.

**EVIDENCE**  
Inspection of `AutomationController._register_routes()` confirms only `/api/automation/disable` is registered. Calling `POST /api/automation/add` for a disabled report returns HTTP 409 Conflict ("already exists"). The only mechanism available to re-enable a disabled report is `POST /api/automations/reset`, which unconditionally terminates all running processes across all lanes, wipes `day.reports_ran`, and resets every automation in the catalog to `Waiting`.

**CONSEQUENCE**  
Once an operator disables an individual report, it cannot be resumed or re-enabled without performing a full, destructive operational reset that terminates active production jobs and clears the daily execution slate.

**VERIFICATION CRITERION**  
An operator must be able to re-enable an individually disabled automation via dedicated API without triggering a destructive global scheduler reset or terminating in-flight jobs.
