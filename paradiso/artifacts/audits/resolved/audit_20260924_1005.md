## 3. FINDINGS DETAILS

### F-015: Receipt JSON Field Naming Divergence Between Blueprint and New Reports

- **Severity:** LOW
- **Confidence:** CONFIRMED
- **Category:** RECEIPT CONTRACT / DOC-DRIFT
- **Invariant:** I-7 (Honest API), I-8 (Queue / Storage / Memory Convergence)
- **Location:** `reports/credit_risk_monitor.py:20-28`, `reports/daily_cash_flow.py:20-28`, `reports/portfolio_summary.py:20-28`, `paradiso/models/report_log.py:78-99`

#### OBSERVATION
The three new report scripts in `reports/` (`credit_risk_monitor.py`, `daily_cash_flow.py`, `portfolio_summary.py`) emit JSON receipts using non-canonical field names:
- `"report_name"` instead of `"name"`
- `"timestamp"` instead of `"last_run"`
- `"message"` instead of `"last_output"`
- Missing `"duration"`
- Missing `"reason"`

#### EVIDENCE
In `paradiso/storage/automations.json`, lines 28, 42, and 56 confirm that `last_output` fell back to raw stdout process capture rather than reading the receipt payload:
```json
"last_output": "[00:23:57] Starting Daily Cash Flow extraction...\n[00:23:57] Connecting to treasury ledgers...\n[00:23:57] Reconciled accounts: Inflows=$3,120,450.75, Outflows=$1,890,200.25\n[00:23:57] Net Closing Cash Position: $15,480,250.50\n[00:23:57] Receipt persisted to paradiso/logs/Daily Cash Flow.json."
```
Whereas canonical reports (`sample_report_blueprint.py`) cleanly populate structured single-line output:
```json
"last_output": "SF Base completed in 0.0s. Successfully processed 1500 records for 20260924."
```

#### CONSEQUENCE
While execution completes with exit 0, structured metadata (metrics, deliverables, summary reasons) is lost from `automations.json` and timeline audit events.

#### VERIFICATION CRITERION
`ReportLog.from_json()` reads fallback fields (`data.get("last_output") or data.get("message")`, `data.get("last_run") or data.get("timestamp")`), OR report scripts are standardized to the Section 12 canonical specification.

### F-016: PoC Verification Scripts Mutated Live Production `storage/intraday.json`

- **Severity:** MEDIUM
- **Confidence:** CONFIRMED
- **Category:** TEST HYGIENE / STORAGE INTEGRITY
- **Invariant:** I-6 (Storage Atomicity & Durability), I-8 (Queue / Storage / Memory Convergence)
- **Location:** `artifacts/audits/poc/poc_f010_verification.py:129`, `artifacts/audits/poc/poc_bg001_bg002_verification.py:20`, `artifacts/audits/poc/poc_f001_verification.py:24`, `storage/intraday.json:509-534`

#### OBSERVATION
Adversarial PoC scripts `poc_f010_verification.py`, `poc_bg001_bg002_verification.py`, and `poc_f001_verification.py` previously instantiated `create_app()` without an isolated `storage_dir` or `PARADISO_STORAGE_DIR` environment variable. Running vector 3 of `poc_f010_verification.py` directly injected synthetic future test dates into the live working tree's `paradiso/storage/intraday.json`.

#### EVIDENCE
Inspecting `paradiso/storage/intraday.json` (lines 509–534) reveals persistent synthetic entries:
```json
    "2048-06-24": {
        "status": "WAITING_TO_OPEN",
        "expected_reports": [],
        "reports_ran": {},
        "timeline": [
            {
                "timestamp": "12:11 AM",
                "title": "Day Initialized",
                "description": "Paradiso day initialized for 2048-06-24 (All reports reset to Waiting)",
                "type": "system"
            }
        ]
    },
    "2048-06-13": { ... }
```

#### CONSEQUENCE
Violates Auditor constraint 2 ("Reproductions must run against isolated temporary storage. Never against the live working tree's storage"). Pollutes production history queries (`/api/executions/history`) with year-2048 test days.

#### STATUS & REMEDIATION
- **Auditor Action Taken:** Refactored `poc_f010_verification.py`, `poc_bg001_bg002_verification.py`, and `poc_f001_verification.py` to construct and clean isolated `tempfile.TemporaryDirectory` paths with `create_app(storage_dir=...)`. All PoCs now run with 100% storage isolation.
- **Builder Action Required:** Safely purge the bogus `"2048-06-24"` and `"2048-06-13"` keys from `paradiso/storage/intraday.json`.

### F-017: Unit Test Executions Contaminate Production `paradiso/logs/` with Test Receipts

- **Severity:** LOW
- **Confidence:** CONFIRMED
- **Category:** LOG HYGIENE / TEST LEAKAGE
- **Invariant:** I-7 (Honest API), I-8 (Queue / Storage / Memory Convergence)
- **Location:** `paradiso/models/report_log.py:10`, `paradiso/services/execution_service.py:40-58`

#### OBSERVATION
`ReportLog.__init__()` defaults `self.log_dir` to `BASE_DIR / "logs"` (`paradiso/logs/`). `ExecutionService.execute_report` instantiates `ReportLog(name)` directly, with no parameter or hook for redirecting receipt generation during test runs.

#### EVIDENCE
Listing `paradiso/logs/` reveals 10 files, of which 6 are test artifacts created by unit tests in `tests/test_audit_fixes.py` and `tests/test_services.py`:
- `BrokenReport.json` (from `test_max_retry_limit_prevents_infinite_spin`)
- `EscapedReport.json` (from path sanitization tests)
- `Missing_Report.json` (from `test_missing_report`)
- `Report_Alpha.json` (from `test_services.py`)
- `SpamReport.json` (from timeline event deduplication tests)
- `Delinquency_RollRate.json` (legacy test report)

Only 4 correspond to actual automations (`Credit Risk Monitor.json`, `Daily Cash Flow.json`, `Portfolio Summary.json`, `SF Base.json`).

#### CONSEQUENCE
Production log folder becomes cluttered with fake failure receipts and test residues. In automated log archival, test artifacts could trigger false alerting.

#### VERIFICATION CRITERION
`ExecutionService` and `ReportLog` support an optional `log_dir` override (or inherit from an environment variable `PARADISO_LOGS_DIR`), allowing test suites to direct receipts to temporary directories.

### F-018: Missing `.gitignore` & Committed Bytecode Artifacts

- **Severity:** LOW
- **Confidence:** CONFIRMED
- **Category:** REPOSITORY HYGIENE
- **Invariant:** I-9 (Security Boundaries / Environment Hygiene)
- **Location:** Workspace root and `paradiso/`

#### OBSERVATION
No `.gitignore` exists anywhere in the repository. As a consequence, Python bytecode cache directories (`__pycache__`) and compiled `.pyc` files have been tracked and staged in git:
- `paradiso/__pycache__/app.cpython-312.pyc`
- `paradiso/models/__pycache__/automation.cpython-312.pyc`
- `paradiso/models/__pycache__/intraday.cpython-312.pyc`
- `paradiso/services/__pycache__/intraday_service.cpython-312.pyc`
- `paradiso/tests/__pycache__/*.pyc`

Additionally, new pipeline scripts (`reports/credit_risk_monitor.py`, `reports/daily_cash_flow.py`, `reports/portfolio_summary.py`) and log receipts are untracked.

#### CONSEQUENCE
Repository bloat, cross-platform cache contamination, and risk of merge conflicts over binary files.

#### VERIFICATION CRITERION
A root `.gitignore` is created ignoring `__pycache__/`, `*.pyc`, `*.pyo`, `.pytest_cache/`, and ephemeral scratch files; tracked `.pyc` files are removed with `git rm --cached`.

#### VERIFICATION CRITERION
`run_tests.py` is implemented as a standard `unittest` test runner wrapper, or `TECHNICAL_DOCUMENTATION.md` is updated to prescribe `python -m unittest discover tests` with the accurate 76-test count.
