## 3. New Active Findings Dossier (Standard Triad)

### [F-031] Cold Boot Leaks Prior Day's Completed Status in Automations Catalog into Lane C `type_c_ran_today`, Suppressing Daily Execution

- **Severity:** CRITICAL
- **Confidence:** CONFIRMED
- **Category:** COLD BOOT & STORAGE LEAK
- **Invariant:** I-1, I-4, Lane C Daily Execution Invariant
- **Location:** `paradiso/services/intraday_service.py:_hydrate_type_c_ran_today:208-210`
- **Replication Asset:** [`paradiso/artifacts/audits/poc/poc_f031_cold_boot_lane_c_leak.py`](file:///c:/Users/desktop/Documents/work/celestial_rose/paradiso/artifacts/audits/poc/poc_f031_cold_boot_lane_c_leak.py)

#### OBSERVATION
In `intraday_service.py:_hydrate_type_c_ran_today(date)`, lines 208–210 unconditionally iterate through `self.automation_service.get_by_type("type_c")` and add any report with `r.status == "Completed"` directly to `self.type_c_ran_today`.

On a cold boot of a new calendar day (e.g. server started at 07:30 AM), `automations.json` still retains the `"Completed"` status from yesterday's successful run because `set_waiting_all()` has not yet executed. Consequently, `_hydrate_type_c_ran_today` prematurely flags yesterday's completed Lane C reports as already completed today.

#### EVIDENCE
Demonstrated deterministically in `poc_f031_cold_boot_lane_c_leak.py`:
1. `automations.json` contains `EOD Ledger Reconciliation` with `status: "Completed"` from yesterday.
2. `intraday.json` has no day record yet for today (cold boot).
3. Upon instantiation, `IntradayService` populates `self.type_c_ran_today = {"EOD Ledger Reconciliation"}`.
4. When `start_lane("type_c")` is called, `self.type_c_ran_today` is never cleared.
5. When clock advances to `20:30`, `tick()` evaluates `if rep.name in self.type_c_ran_today: continue`.
6. Dispatched reports list is `[]`. The report is never executed today.

#### CONSEQUENCE
Any Lane C timeslot report (e.g., daily cash reconciliation, mid-day ledger feeds, EOD books) that completed successfully yesterday will be completely suppressed and fail to execute on any day where the service is cold-booted, directly violating Invariant I-4 ("Cold boot never leaks prior day completion") and the Lane C Daily Execution Invariant.

#### VERIFICATION CRITERION
`type_c_ran_today` must only be hydrated from records in `intraday.json` corresponding to the current calendar date (`CLOCK.date_str()`). It must never inspect the persistent `status` property in `automations.json` without verifying that the run finished on the current calendar date.

### [F-032] Fragile Exact-String Matching in `_get_or_init_day` Causes Storage Paralysis When Pre-existing Closed Day Contains Realistic Cutoff Reasons

- **Severity:** HIGH
- **Confidence:** CONFIRMED
- **Category:** STORAGE PARALYSIS EVASION
- **Invariant:** I-4, I-6, I-8
- **Location:** `paradiso/services/intraday_service.py:_get_or_init_day:228-233`
- **Replication Asset:** [`paradiso/artifacts/audits/poc/poc_f032_f028_fragile_string_paralysis.py`](file:///c:/Users/desktop/Documents/work/celestial_rose/paradiso/artifacts/audits/poc/poc_f032_f028_fragile_string_paralysis.py)

#### OBSERVATION
In `intraday_service.py:_get_or_init_day()`, lines 228–233 implement a condition to detect stale closed day records during `OPEN` or `force_open`:
```python
elif (status == Intraday.OPEN or force_open) and day.status == Intraday.CLOSED:
    all_auto_finalized = len(day.reports_ran) > 0 and all(
        getattr(r, "reason", "") == "Historical day finalized automatically"
        for r in day.reports_ran.values()
    )
    if all_auto_finalized or len(day.reports_ran) == 0:
        is_stale_or_premature = True
```
This check fragilely matches only the synthetic string from the auditor's PoC (`"Historical day finalized automatically"`). If a pre-existing closed day record in `intraday.json` contains realistic reasons emitted by Paradiso's own `_close_day()` (such as `"Not completed before 10:00 PM cutoff"` or `"Forcibly terminated: breached 10:00 PM cutoff (exceeded grace window)"`) or runtime errors, `all_auto_finalized` evaluates to `False`.

#### EVIDENCE
Demonstrated deterministically in `poc_f032_f028_fragile_string_paralysis.py`:
1. `intraday.json` contains today's date with `status: "CLOSED"` and reports in `reports_ran` with `reason: "Not completed before 10:00 PM cutoff"`.
2. When `start_lane("type_a", force_open=True)` is called, `is_stale_or_premature` evaluates to `False`.
3. `_get_or_init_day()` does not cleanse `reports_ran`.
4. `already_ran = set(day.reports_ran.keys())` excludes all pending reports.
5. `self.waitlist` has length `0`, causing complete queue paralysis.

#### CONSEQUENCE
Whenever a day record is prematurely closed with realistic production reasons, the engine fails to cleanse the record, leaving the queue paralyzed and preventing all daily reports from running.

#### VERIFICATION CRITERION
When `status == Intraday.OPEN` (or `force_open` is active) during morning operational hours or upon explicit lane activation, any pre-existing record for today marked `CLOSED` where no genuine successful runs completed today must be cleansed to a clean slate, regardless of the historical failure reason string.

### [F-033] Unbounded Stickiness of `force_open` Across Independent Lane Lifecycles Bypasses 22:00 Hard Cutoff and Mutates Status Machine

- **Severity:** HIGH
- **Confidence:** CONFIRMED
- **Category:** STATE MACHINE & SAFETY BOUNDARY
- **Invariant:** I-3, I-5, I-7
- **Location:** `paradiso/services/intraday_service.py:start_lane:288-290`, `stop_lane:331-393`, `resolve_status:262-263`
- **Replication Asset:** [`paradiso/artifacts/audits/poc/poc_f033_sticky_force_open_cutoff_bypass.py`](file:///c:/Users/desktop/Documents/work/celestial_rose/paradiso/artifacts/audits/poc/poc_f033_sticky_force_open_cutoff_bypass.py)

#### OBSERVATION
When any lane is started with `force_open=True` (e.g. `POST /api/paradiso/lane/start {"lane": "type_b", "force_open": true}`), `self.force_open` is set to `True` globally on `IntradayService`. When the lane is stopped via `POST /api/paradiso/lane/stop {"lane": "type_b"}`, `self.force_open` is **never reset to `False`**.

Because `resolve_status()` returns `Intraday.OPEN` unconditionally whenever `self.force_open == True`:
1. The status at 22:30 PM resolves to `OPEN` rather than `CLOSED`.
2. The 22:00 hard cutoff in `tick()` (`if status == Intraday.CLOSED:`) is never reached, and `_close_day()` is never invoked.
3. Lingering subprocesses are never terminated.
4. Midnight rollover initializes the next calendar day as `OPEN` at 00:05 AM in the middle of the night instead of `WAITING_TO_OPEN`.
5. Other lanes can be started outside window hours without supplying `force_open`.

#### EVIDENCE
Demonstrated deterministically in `poc_f033_sticky_force_open_cutoff_bypass.py`:
1. Start Lane B with `force_open=True`, then stop Lane B. `intra_svc.force_open` remains `True`.
2. At 22:30 PM, `resolve_status()` returns `OPEN`.
3. `intra_svc.tick()` executes without setting `day_closed = True`.
4. Crossing midnight to 00:05 AM initializes new day with `day.status == "OPEN"`.

#### CONSEQUENCE
A single forced execution of any lane permanently destroys the 24-hour state machine invariants for the lifetime of the process, preventing evening hard cutoffs, failing to kill runaway tasks at 22:00, and causing uncoordinated midnight runs.

#### VERIFICATION CRITERION
`force_open` must not be a persistent sticky flag that outlives the active execution of the lane that requested it. When all lanes are stopped, or upon reaching the 22:00 cutoff boundary, forced overrides must yield to safety cutoffs.

### [F-034] Actively Executing Type B and Type C Reports Can Be Deleted via `DELETE /api/automation/delete/<name>`, Leaving Orphaned Host Processes

- **Severity:** MEDIUM
- **Confidence:** CONFIRMED
- **Category:** INTEGRITY & PROCESS ORPHANING
- **Invariant:** I-5, I-8, BG-001
- **Location:** `paradiso/controllers/automation_controller.py:delete_automation:114-126`
- **Replication Asset:** [`paradiso/artifacts/audits/poc/poc_f034_delete_active_report_orphaning.py`](file:///c:/Users/desktop/Documents/work/celestial_rose/paradiso/artifacts/audits/poc/poc_f034_delete_active_report_orphaning.py)

#### OBSERVATION
In `AutomationController.delete_automation()`, the catalog lock check is:
```python
if self.intraday_service and self.intraday_service.is_active:
    return 409
```
When a Type B or Type C report is running on-demand (`POST /api/automation/run`) while scheduler lanes are paused, `self.intraday_service.is_active` evaluates to `False` (even though `self.intraday_service.has_active_runs` is `True`).

Furthermore, `delete_automation()` only pops `self.intraday_service.current_runs` (Lane A) and never cleans up `active_runs_type_b` or `active_runs_type_c`, nor does it invoke `runner.kill_process()`.

#### EVIDENCE
Demonstrated deterministically in `poc_f034_delete_active_report_orphaning.py`:
1. Register Type B automation and simulate active execution. `has_active_runs` is `True`, `is_active` is `False`.
2. `DELETE /api/automation/delete/<name>` returns HTTP 200 OK.
3. The report is deleted from `automations.json` while the host process is still executing.
4. `intra_svc.active_runs_type_b` retains a dangling entry for the deleted report.
5. The underlying OS process continues to execute without supervision.

#### CONSEQUENCE
Host subprocesses are orphaned in the operating system, writing files or consuming database resources while invisible to the catalog. When the subprocess finishes, callbacks attempt to update an automation that no longer exists.

#### VERIFICATION CRITERION
`delete_automation` must inspect `self.intraday_service.has_active_runs` (or whether the target report is present in `current_runs`, `active_runs_type_b`, or `active_runs_type_c`) and return HTTP 409 Conflict if the target report is actively executing.
