## 3. Deep-Dive Vulnerability Dossier

### F-037: Non-Canonical `scheduled_time` Strings Cause Unhandled `ValueError` Crashes or Silent Permanent Execution Starvation

- **Severity:** CRITICAL
- **Invariants Breached:** I-1, I-7, I-9
- **Source Location:** `paradiso/controllers/automation_controller.py:add_automation:92`, `paradiso/services/intraday_service.py:tick:655-657`
- **Adversarial Asset:** `paradiso/artifacts/audits/poc/poc_f037_scheduled_time_format_failures.py`

**OBSERVATION**  
In `AutomationController.add_automation()`, line 92 ingests `scheduled_time` without format validation:
```python
scheduled_time=str(data.get("scheduled_time") or "08:30").strip()
```
In `IntradayService.tick()`, lines 655–657 perform a direct string comparison followed by `datetime.strptime`:
```python
if now_time_str >= target_time:
    target_dt = datetime.combine(now_dt.date(), datetime.strptime(target_time, "%H:%M").time())
    elapsed_minutes = (now_dt - target_dt).total_seconds() / 60.0
```

**EVIDENCE**  
Demonstrated deterministically in `poc_f037_scheduled_time_format_failures.py`:
1. **Crash Vector (12-hour AM/PM format)**: When an operator inputs a 12-hour format string (e.g. `"08:30 AM"`), `add_automation` returns HTTP 201 Created. When `now_time_str >= target_time` evaluates, line 656 executes `datetime.strptime("08:30 AM", "%H:%M")`. This raises an uncaught `ValueError: unconverted data remains: AM`, terminating the `tick()` cycle and crashing the scheduler thread.
2. **Starvation Vector (Unpadded hour)**: When an operator inputs an unpadded hour (e.g. `"8:30"` or `"9:00"`), line 655 evaluates `now_time_str >= target_time`. Because `now_time_str` is formatted with a leading zero (`"%H:%M"`), ASCII string comparison evaluates `'08:30' >= '8:30'` as `False`. In fact, every 24-hour timestamp from `'00:00'` to `'23:59'` evaluates to `False` against `'8:30'`. The condition is never satisfied at any minute of the day. The report is silently ignored and never dispatched.

**CONSEQUENCE**  
User input formatting variations either crash the background daemon loop with unhandled exceptions or permanently starve timeslot reports from ever dispatching.

**VERIFICATION CRITERION**  
`add_automation` must validate `scheduled_time` format, enforcing canonical 24-hour `HH:MM` syntax (`00:00` to `23:59`) and rejecting non-conforming inputs with HTTP 400 Bad Request. `tick()` must handle timeslot evaluation defensively without raising unhandled exceptions or failing string comparisons.

### F-038: `POST /api/automation/add` Silently Discards `catch_up_policy` Parameter

- **Severity:** MEDIUM
- **Invariants Breached:** I-7, I-8
- **Source Location:** `paradiso/controllers/automation_controller.py:add_automation:85-98`
- **Adversarial Asset:** `paradiso/artifacts/audits/poc/poc_f038_catch_up_policy_dropped_in_api.py`

**OBSERVATION**  
While the `Report` dataclass model (`models/report.py:21`) supports an optional `catch_up_policy: Optional[str]`, `AutomationController.add_automation()` does not extract or pass `catch_up_policy` from the incoming JSON payload `data` when instantiating `Report`.

**EVIDENCE**  
Demonstrated deterministically in `poc_f038_catch_up_policy_dropped_in_api.py`. Submitting `POST /api/automation/add` with:
```json
{
    "name": "Policy_Drop_Test",
    "report_type": "type_c",
    "catch_up_policy": "SKIP_UNTIL_NEXT_DAY",
    ...
}
```
returns HTTP 201 Created with `"catch_up_policy": null` in the serialized report, and `automations.json` persists the report with `catch_up_policy: null`.

**CONSEQUENCE**  
Operators and API clients cannot configure per-report catch-up policies as specified in Milestone P2.2; the parameter is dropped silently without notice or error.

**VERIFICATION CRITERION**  
`add_automation` must accept, validate, and persist `catch_up_policy` when supplied in the request payload, returning HTTP 400 Bad Request if an unrecognized policy string is provided.

### F-039: `reset_all_reports()` Fails to Clear `self.type_c_warned`, Permanently Silencing Warnings Post-Reset

- **Severity:** MEDIUM
- **Invariants Breached:** I-4, I-7, I-8
- **Source Location:** `paradiso/services/intraday_service.py:reset_all_reports:481-498`
- **Adversarial Asset:** `paradiso/artifacts/audits/poc/poc_f039_reset_all_reports_type_c_warned_retention.py`

**OBSERVATION**  
In `IntradayService.reset_all_reports()`, lines 488–498 reset `waitlist`, `retry_counts`, `type_b_last_run`, `type_c_ran_today`, and `type_c_retry_after`. However, `self.type_c_warned` is not cleared.

**EVIDENCE**  
Demonstrated deterministically in `poc_f039_reset_all_reports_type_c_warned_retention.py`. When a report with policy `WARN_OPERATOR` exceeds its grace window, it is added to `self.type_c_warned`. Calling `reset_all_reports()` (or `POST /api/automations/reset`) leaves `rep_name` in `self.type_c_warned`. On subsequent ticks, line 697 (`if rep.name not in self.type_c_warned:`) evaluates to `False`. No further warning timeline event is generated.

**CONSEQUENCE**  
Following an operational reset, operators are never alerted if the timeslot continues to be missed, giving the false appearance of normal execution.

**VERIFICATION CRITERION**  
`reset_all_reports()` must clear `self.type_c_warned` alongside other per-day tracking collections to ensure complete state synchronization.
