## 1. Executive Summary

Batch 7 remediations for F-040 (Disabled report manual run bypass), F-041 (Lane B infinite dispatch loop), and F-042 (Simulation reset idle guardrail) have been applied and verified through PoC regression and full test suite execution (131/131 passing).

## 2. Remediation Assessment Detail

### F-040: `POST /api/automation/run` Bypasses "Disabled" State — **RESOLVED (HIGH LONGEVITY)**

**Changes Applied:**
- `execution_controller.py:38-42`: Added `if getattr(report, "status", "") == "Disabled": return 409`
- `intraday_service.py:1200`: Added `getattr(report, "status", "") == "Disabled"` to `trigger_manual_run` guard

**Longevity Assessment:**
- **Dual-layered defense**: Controller blocks at HTTP boundary AND service layer independently rejects. Even if one layer is bypassed (e.g., internal caller), the other catches it.
- **No band-aid**: The fix addresses the root cause (missing status check) rather than adding a post-hoc cleanup.
- **Verified via PoC**: `poc_f040_disabled_report_manual_run_bypass.py` now correctly fails (409 != 200) confirming both Type B and Type C disabled reports are rejected.

### F-041: Lane B Infinite Dispatch Loop for Failed Reports — **RESOLVED (WITH BYPASS, SEE F-043)**

**Changes Applied:**
- `intraday_service.py:624`: Changed `if rep.status == "Disabled":` to `if rep.status in ("Disabled", "Failed"):`
- `intraday_service.py:626-627`: Added `if self.retry_counts.get(rep.name, 0) >= self.max_retries: continue`

**Longevity Assessment:**
- **Within a running day session, the fix is robust.** The dual-guard (status check + retry budget check) ensures that permanently failed Lane B reports cannot be automatically dispatched.
- **Structural note**: The status guard (`"Failed"`) is neutralized by `_get_or_init_day → set_waiting_all()` during day initialization, which resets `"Failed"` to `"Waiting"`. However, the `retry_counts` guard compensates within the same session.
- **Bypass discovered (F-043)**: The manual run path (`trigger_manual_run`) does not check for `"Failed"` status. A successful manual run resets `retry_counts` to 0 and sets status to `"Completed"`, bypassing both guards.
- **Verified via PoC**: `poc_f041_lane_b_infinite_exhausted_dispatch.py` now correctly fails, confirming the infinite loop is blocked within a same-day session.

### F-042: `POST /api/settings/simulation/reset` Bypasses BG-001 — **RESOLVED (HIGH LONGEVITY)**

**Changes Applied:**
- `settings_controller.py:78-89`: Added BG-001 idle-only check mirroring `update_settings()` guard.

**Longevity Assessment:**
- **Structurally identical to existing guardrail**: The code is a direct replication of the proven `update_settings()` BG-001 check at lines 36-47.
- **Multi-source activity detection**: Checks `paradiso.is_running()` (thread-level) AND `intraday_service.is_active` (lane-level) AND `has_active_runs` (in-flight jobs). All three detection vectors are covered.
- **Verified via PoC**: `poc_f042_simulation_reset_bypasses_idle_guardrail.py` now correctly fails (409 != 200) confirming both scheduler-active and jobs-in-flight scenarios are rejected.

## 3. New Finding: F-043

### F-043: Manual Run of Failed Lane B Report Silently Re-Arms Automatic Dispatch

- **Severity:** MEDIUM
- **Invariants Breached:** I-1, I-8
- **Source Location:** `paradiso/services/intraday_service.py:trigger_manual_run:1197-1218`, `paradiso/services/intraday_service.py:_trigger_type_b_report._on_good:959-966`, `paradiso/controllers/execution_controller.py:run_automation:38-42`
- **Adversarial Asset:** `paradiso/artifacts/audits/poc/poc_f043_manual_run_rearms_failed_report.py`

#### OBSERVATION
The F-040 fix correctly blocks manual execution of `"Disabled"` reports. The F-041 fix correctly blocks automatic dispatch of `"Failed"` reports in `tick()`. However, neither `ExecutionController.run_automation()` nor `IntradayService.trigger_manual_run()` checks for `report.status == "Failed"`. This creates a side-channel:

In `execution_controller.py:38-42`, the disabled check:
```python
if getattr(report, "status", "") == "Disabled":
    return ..., 409
```
does not cover `"Failed"`.

In `intraday_service.py:1200`, the guard:
```python
if not report or report.report_type == "type_a" or getattr(report, "status", "") == "Disabled":
    return False
```
also does not cover `"Failed"`.

When `_trigger_type_b_report._on_good()` fires after a successful manual run (line 966):
```python
self.retry_counts[name] = 0
```
and `ExecutionService.execute_report()` sets `status = "Completed"` (line 83), both F-041 guard conditions are reset. On the next `tick()` interval cycle, `status="Completed"` passes the `("Disabled", "Failed")` check, and `retry_counts=0` passes the `>= max_retries` check.

#### EVIDENCE
Demonstrated deterministically in `poc_f043_manual_run_rearms_failed_report.py`:
1. Register a Type B report with `interval_minutes: 15` and `max_retries: 3`.
2. Initialize the day via `tick()` (establishes the intraday record).
3. Exhaust retries: set `status="Failed"`, `retry_counts=3`. Verify `tick()` does NOT dispatch (F-041 fix working).
4. Simulate a successful manual run: set `retry_counts=0`, `status="Completed"`, update `type_b_last_run`.
5. Advance clock by 20 minutes (exceeding `interval_sec=900`).
6. Call `tick()`. The report is dispatched again automatically.

**PoC output:**
```
rearm_dispatched: ['Failed_B_Report']
Report status: Completed
retry_counts: {'Failed_B_Report': 0}
```

#### CONSEQUENCE
A Lane B report that has permanently failed and exhausted its retry budget can be silently resurrected for automatic interval dispatch by a single successful manual run. The operator who triggered the manual run would not be aware that this also re-arms continuous automatic scheduling. The `"Failed"` terminal state is not truly terminal — it can be silently undone through the manual run pathway.

#### VERIFICATION CRITERION
Either (a) `trigger_manual_run()` and `ExecutionController.run_automation()` must reject manual execution of `"Failed"` reports, OR (b) the manual run success callback must NOT reset `retry_counts` to 0, preserving the exhausted retry budget so `tick()` continues to suppress automatic dispatch. If deliberate re-enablement of a `"Failed"` report is desired, it should require an explicit administrative action (e.g., `POST /api/automation/enable`-like pathway) distinct from a manual one-off execution.
