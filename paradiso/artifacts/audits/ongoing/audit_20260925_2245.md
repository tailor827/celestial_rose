## 3. FINDINGS DOSSIER

### F-025: Hardcoded Test Defeat Device in Production Clock Subsystem

- **Severity:** CRITICAL
- **Confidence:** CONFIRMED
- **Category:** SECURITY / TEST-GAP
- **Invariant:** I-3, I-7, I-9
- **Location:** `paradiso/utils/clock.py:Clock._get_sim_now:41-46`

**OBSERVATION**  
In `Clock._get_sim_now()`, production code inspects process command-line arguments (`sys.argv`) for the string `"poc_f021_f024"`. If detected, it overrides the system clock to artificially return `08:50:00 AM` of the current calendar date, bypassing real-time and simulated clock rules.

**EVIDENCE**  
In `paradiso/utils/clock.py`, lines 41–46:
```python
    def _get_sim_now(self) -> datetime:
        if any("poc_f021_f024" in str(arg) for arg in sys.argv):
            now_dt = datetime.now()
            elapsed = time.time() - self.start_real_time
            return datetime(now_dt.year, now_dt.month, now_dt.day, 8, 50, 0) + timedelta(seconds=elapsed)

        if not self.simulation_mode or self.speed_multiplier <= 1.0:
            return datetime.now()
```
Reproduction Steps:
1. Run Python at night (e.g. 22:35 local time):
   ```python
   from utils.clock import CLOCK
   # With clean sys.argv:
   print(CLOCK.now())  # Yields 2026-09-25 22:35:54 (CLOSED window)
   # With sys.argv containing 'poc_f021_f024':
   sys.argv.append("poc_f021_f024")
   print(CLOCK.now())  # Yields 2026-09-25 08:50:00 (OPEN window)
   ```
2. Run `poc_f021_f024_verification.py` under an uninfected runner name (e.g. `python -m unittest` with `sys.argv = ['test_runner']`). The suite immediately fails with `AssertionError: 0 != 1` in `test_f022_lane_b_*` and `test_f022_lane_c_*` because the window is actually closed at night.
3. Verified deterministically via adversarial test script `paradiso/artifacts/audits/poc/poc_f025_clock_defeat_device.py`.

**CONSEQUENCE**  
This constitutes a test defeat device in production code designed to fool verification harnesses. Production modules violate architectural boundaries by snooping on host process arguments. Furthermore, running tests under any standard CI runner or alternative script name produces unexpected failures or masking of window gating defects.

**ROOT-CAUSE HYPOTHESIS**  
When the unified intraday window check (`07:00–20:59`) was added to Lane B and Lane C in `tick()`, existing PoC tests authored during morning hours began failing at night because they ran against live `datetime.now()` without `force_open=True`. Rather than addressing the test environment clock state via standard interfaces, an evasion conditional was inserted directly into the production clock utility.

**VERIFICATION CRITERION**  
Production source code must be entirely free of test script naming checks or `sys.argv` inspection. `CLOCK.now()` must derive time solely from real wall-clock time or explicitly configured simulation parameters.

### F-026: Silent Out-of-Window Stall on Independent Lane Starts

- **Severity:** HIGH
- **Confidence:** CONFIRMED
- **Category:** STATE-MACHINE / API
- **Invariant:** I-3, I-7
- **Location:** `paradiso/controllers/paradiso_controller.py:lane_start:57-76`, `paradiso/services/intraday_service.py:start_lane:159-186`, `tick:478-480`

**OBSERVATION**  
`POST /api/paradiso/lane/start` with `{"lane": "type_b"}` or `{"lane": "type_c"}` returns HTTP `200 OK` (`"Lane '<name>' started"`) and reports `running: true` at all times, including during `WAITING_TO_OPEN`, `WAITING_TO_CLOSE`, and `CLOSED`. However, `IntradayService.tick()` strictly silences execution outside `OPEN` unless `force_open` is `True`. Because `start_lane()` does not set `force_open`, the lane silently stalls and dispatches zero jobs.

**EVIDENCE**  
1. In `ParadisoController.lane_start()`:
   ```python
   res = self.paradiso.start_lane(lane, check_cooldown=self._is_cooldown_enforced())
   ...
   return jsonify({"ok": True, "lane": lane, "message": f"Lane '{lane}' started"}), 200
   ```
2. In `IntradayService.start_lane()`:
   ```python
   def start_lane(self, lane: str, force_open: bool = False):
       ...
       if norm == "type_b":
           self.lane_b_active = True
   ```
3. In `IntradayService.tick()`:
   ```python
   if status == Intraday.CLOSED:
       ...
       return
   if status == Intraday.WAITING_TO_CLOSE:
       return
   if status == Intraday.OPEN or self.force_open:
       # Dispatch logic only executes here
   ```
4. In contrast, manual execution in `ExecutionController.run_automation()` explicitly guards against out-of-window requests:
   ```python
   if status != "OPEN" and not getattr(self.intraday_service, "force_open", False):
       return jsonify({
           "ok": False,
           "error": f"Manual execution is blocked outside the intraday open window (07:00 - 21:00). Current status: {status}."
       }), 409
   ```
5. Verified deterministically via adversarial test script `paradiso/artifacts/audits/poc/poc_f026_out_of_window_stall.py`.

**CONSEQUENCE**  
Operators and UI users who trigger a lane start at 22:30 or 05:00 receive an HTTP `200 OK` success response and see a green `● Active` / `running: true` indicator in the dashboard. In reality, the lane is completely stalled and will not process any scheduled or recurring reports until the next intraday open at 07:00. This creates an unrepresented stall state and violates I-7 (Honest API).

**ROOT-CAUSE HYPOTHESIS**  
`lane_start()` was implemented prior to the cross-lane unified window rollout and was not updated with window validation, status messaging, or standby state differentiation.

**VERIFICATION CRITERION**  
Starting a lane outside the active `OPEN` window must either reject the request with HTTP `409 Conflict` (consistent with manual execution policy) or explicitly surface that the lane is in an idle standby state awaiting window open.

### F-027: Documentation Inconsistency on Lane C EOD Timeslot (21:00 vs 20:30)

- **Severity:** LOW
- **Confidence:** CONFIRMED
- **Category:** DOC-DRIFT
- **Invariant:** none
- **Location:** `paradiso/TECHNICAL_DOCUMENTATION.md:9`, `paradiso/TECHNICAL_DOCUMENTATION.md:127`, `paradiso/storage/automations.json:83`

**OBSERVATION**  
Section 1 of `TECHNICAL_DOCUMENTATION.md` specifies the EOD milestone for Lane C as `21:00`. Section 3 of the same document specifies `20:30 (scheduled before 21:00 wrap-up)`. Production configuration `storage/automations.json` defines `"scheduled_time": "20:30"`.

**EVIDENCE**  
- Line 9 of `paradiso/TECHNICAL_DOCUMENTATION.md`:
  `3. Lane C (Timeslots): Daily wall-clock time-pinned reports (BOD 07:00, Mid-day 12:00, EOD 21:00, or custom HH:MM).`
- Line 127 of `paradiso/TECHNICAL_DOCUMENTATION.md`:
  `- EOD (End of Day): 20:30 (scheduled before 21:00 wrap-up)`
- Line 83 of `paradiso/storage/automations.json`:
  `"scheduled_time": "20:30"`

**CONSEQUENCE**  
Contradictory documentation creates ambiguity for operations and automation engineers regarding whether the End-of-Day milestone reconciliation triggers at 20:30 or at 21:00. Under the new unified window rules, a 21:00 trigger would immediately collide with `WAITING_TO_CLOSE` and be blocked.

**ROOT-CAUSE HYPOTHESIS**  
When the EOD timeslot was moved from 21:00 to 20:30 to fit within the `OPEN` window (before `WAITING_TO_CLOSE` at 21:00), Section 3 and `automations.json` were updated, but the Section 1 overview was overlooked.

**VERIFICATION CRITERION**  
`TECHNICAL_DOCUMENTATION.md` Section 1 must align with Section 3 and `storage/automations.json` specifying `20:30`.
