7. ARCHITECTURAL DISCIPLINE
==================================================

Respect the existing 4-tier architecture:

1. Web UI Layer (`web/static/js/app.js`, `web/templates/index.html`, `web/static/css/style.css`):
   - Single Page Application communicating via REST API endpoints.
   - Responsible for rendering metrics, execution tables, timelines, and settings.
2. Controller Layer (`controllers/`):
   - Handles route registrations, parses HTTP request payloads, performs input validation, returns standardized JSON responses and proper HTTP status codes.
   - Must delegate business operations to the Services Layer.
3. Services Layer (`services/`):
   - Contains core business logic, intraday state machine management (`IntradayService`), scheduling loops (`Paradiso`), execution orchestration (`ExecutionService`), and process supervision (`Runner`).
4. Models & Storage Layer (`models/`, `storage/`):

5. Utilities (`utils/`):
   - Cross-cutting concerns such as simulation clock (`CLOCK`) and configuration (`CONFIG`).

Before changing architecture:

3. Determine the actual architectural failure.
4. Prefer the smallest architectural change that correctly resolves the underlying problem.
5. Avoid unnecessary abstractions.

==================================================
8. DATA CONSISTENCY & STORAGE SAFETY
==================================================

When working with persistence, race condition safety is a primary engineering concern.

Pay particular attention to:

- Concurrent mutations between the background scheduler daemon and incoming HTTP API requests
- Atomic file write-replace operations via `StorageBase.mutate()`
- Preventing file corruption and ensuring `.bak` rescue copies on decode errors
- Windows file lock contention and retry backoff behavior
- Stale reads vs live in-memory queue state (`waitlist`, `current_runs`)
- Cold boot reconciliation and historical unclosed days finalization
- Midnight reset synchronization across `automations.json` and `intraday.json`

The Web UI and API must never report an operation as successful when persistence or queue dispatch has failed.


==================================================
9. STATE MANAGEMENT & QUEUE DISCIPLINE
==================================================

Respect the project's existing state-management architecture.

Inspect:

- State ownership between `IntradayService`, `AutomationService`, and `ExecutionService`
- Intraday state machine transitions (`WAITING_TO_OPEN` -> `OPEN` -> `WAITING_TO_CLOSE` -> `CLOSED`)
- Sequential execution policy: strictly 1 report executing at any time during intraday (`len(current_runs) == 0`)
- Retrial threshold vs dependency wait handling:
  - **Reports waiting for dependencies**: When a report outputs `SKIPPED: Missing dependency 'X'`, it must be rotated to the back of `self.waitlist` to allow independent reports to run. This is a transient wait and MUST NOT increment the error retry counter.
  - **Reports with errors/crashes**: When a report fails with an exit code != 0 or process exception, increment its attempt count. If attempts < `max_retries` (default: 3), set status to `Retrial` and re-queue. If attempts >= `max_retries`, mark as terminal `Failed` and do NOT re-queue.
- Sources of truth: do not allow in-memory data structures and stored JSON files to permanently diverge.

State should have a clearly understood owner.


==================================================
10. ASYNC / CONCURRENCY & THREAD SAFETY
==================================================

Look for and correctly handle:

- Thread synchronization using `threading.RLock`
- Re-entrant locking across nested service calls
- Race conditions between background daemon loops and REST controller endpoints
- Safe process termination during manual stop, test reset, or 10:00 PM cutoff
- Suppression of false failure callbacks when processes are intentionally terminated
- Deadlock prevention across Clock, Storage, and Runner subsystems

Do not assume sequential behavior where multi-threaded execution occurs.


==================================================
11. ERROR HANDLING
==================================================

Errors must be meaningful, observable, and produce standard REST responses.

Do not:

- Silently swallow exceptions
- Convert failures into success
- Catch exceptions without understanding them
- Leave storage or queue state inconsistent after failure
- Hide meaningful diagnostic information
- Add generic error handling that obscures the actual failure

Controllers must return structured JSON:
`{"ok": false, "error": "Descriptive message"}` with appropriate HTTP status codes (400 for bad input, 403 for forbidden actions, 404 for missing items, 409 for conflicts, 500 for internal errors).

12. SECURITY
==================================================

Maintain robust security boundaries:

- Path traversal prevention: sanitize and sandbox any user-supplied report or log identifiers against directory traversal (`..`, `/`, `\`)
- Manual execution restrictions: enforce 403 Forbidden for manual triggers on automated intraday Type A reports to prevent concurrency collisions
- Secret masking: ensure sensitive credentials or tokens in `config.yaml` and `/api/settings` are masked before returning to the client
- Subprocess safety: do not invoke shell execution with unsanitized inputs

Do not weaken security to simplify implementation.
